# SOL-REVIEW-6：P3 step 1–3

## 逐項裁定

- **通過 — Step 1／RecordInfo_SN 共用 builder。** `dispatch/record-info.builder.js:52-64` 先清零完整 `0x60` body，再寫 Level `+0x00`、Coupon `+0x14`、W/D/L/K/D `+0x1c..+0x2c`、Exp `+0x40`、Point `+0x48`；9211 與 30907 分別只在 `account.dispatch.js:529-542`、`gamelogin.dispatch.js:214-227` 呼叫同一函式。同輸入逐位元組相同，9211 的既有錯誤確已消除。
- **需修改 — Step 2／participant 生命週期。** `match-stats.js:115-124` 開場只建立空的 stats map；結算時 `:246-287` 卻從當下的 `room.members` 重建 participants、team、mech 與 `is_test`。非房主若中途斷線並被移出房間，其參戰紀錄、K/D、累加及測試帳號身分全部遺失。應在 `startMatch()` snapshot 參戰者 metadata，之後只更新該 match-owned map；離場不可刪除歷史 participant。
- **需修改 — Step 2／中斷 marker。** socket/正式離房會在 `room-leave.js:93-106` 記 `MATCH-ABORTED`；但戰鬥中的 host 送 `0x00222131` 只走 `gate.game.dispatch.js:1908-1930` → `handleBattleLeave()` `room-leave.js:203-239`，送 EndGame 並切 lobby，沒有呼叫 `emitMatchAborted()`。它不會寫 DB，符合「中斷不持久化」，但漏掉操作者裁定的一行 abort log，且舊 `matchStats` 直到下場才被覆蓋。
- **通過 — Step 2／其餘統計邊界。** start／BeginRound／Death／EndRound／EndGame 分別掛在已 host/dedup-gate 的接受路徑；`closeRound()` 對勝利中間回合及最後勝／敗回合都生效（`match-stats.js:149-215`、`lobby.dispatch.js:440-445,533-539,633-639`）。`MATCH_STATS_MODE` 預設 disabled，關閉時不建狀態、不改封包、不碰 DB。
- **疑點 — Step 3 migration。** 三張表的 DDL、FK 建立順序、`DATETIME`、host `SET NULL` 均合理（`tools/migrate-p3-match-tables.js:45-99,152-165`）。2026-09-20 唯讀查詢確認目前三表不存在；現有 `accounts.id` 是 `INT UNSIGNED`、InnoDB，FK 型別相容。惟 fake test `test/p3-match-tables-migration.js:34-60` 只辨認 SQL 字串，不解析 DDL；正式 DB 前仍須在 disposable MySQL 跑一次。
- **疑點 — migration 冪等性。** `:143-165` 只按表名存在就 skip，不驗欄位、型別、index、FK；這是「fresh current DB 可重跑」，不是 schema convergence。至少建立後應查 `information_schema` 並 fail loudly，避免同名殘表／舊版表被當成功。DDL 跨表不能整體 transaction 屬 MySQL 限制；中途失敗後重跑補缺表的策略可接受。
- **疑點 — participant FK 刪除政策。** `match_participants.account_id ON DELETE CASCADE`（`:84-96`）在技術上有效，但刪帳號會抹掉歷史參戰列，與保留 match 歷史的 host `SET NULL` 方向不同。若這三表是稽核／歷史來源，應改 surrogate PK + nullable account FK `SET NULL`（並保存 account id/name snapshot），或拿掉 accounts FK；若產品明確要求刪帳即刪個資，現狀才可接受。
- **通過 — `recordMatch()` 自身交易。** matches → rounds → participants 在一個 connection/transaction，任一步失敗 rollback 並向外拋（`database/db.js:570-638`）；round／participant FK 或 PK 衝突不會留下半場。
- **需修改 — 整場寫回不是原子操作。** `scheduleMatchWriteback()` 先 commit `recordMatch()`，再逐 participant 呼叫各自 transaction 的 `applyMatchAccumulation()`（`match-stats.js:366-404`；`db.js:669-713`）。中途失敗會留下完整 match rows、但只累加前幾位玩家；process crash 也同樣。**兩者應合併為一個 DB transaction**：同一 connection 插入三表並完成所有非測試 participant 的 records/mech_levels 更新，最後一次 commit。
- **需修改 — UPDATE 靜默零列。** `applyMatchAccumulation()` 不檢查 `affectedRows`（`db.js:675-705`）；缺 records 或錯誤 mechType 會 commit 並回報成功。records 應恰為 1，指定 mechType 時 mech_levels 也應恰為 1，否則 throw 讓整場 transaction rollback。
- **需修改 — `is_test` 裁定只在「仍在房內」時成立。** 9211/30907 的旗標 wiring 正確（`account.dispatch.js:233-239`、`gamelogin.dispatch.js:165-170`），且 `match-stats.js:368-384` 確實先寫三表、再對 is_test 場完全跳過累加；但 `isTest` 由結算時成員計算（`:246-287`），中途離開的 test participant 可讓整場誤判為非測試。修成開場 snapshot 後才符合「host 或任一 participant 是 test，整場只記錄不累加」。
- **疑點 — 時間欄位。** JS `Date` 綁 DATETIME 語法正確（`db.js:587-588,605`），但 pool 沒指定 timezone（`:49-64`）。唯讀查詢顯示目前 MySQL session=`SYSTEM`、system=`CST`，在本機大概與 Asia/Taipei 一致，但部署環境改變可整批偏移；應明定 UTC 或 `+08:00` 並加真 MySQL round-trip test。
- **疑點 — point 語意。** participant 寫 `point_gained = kills*10`（`match-stats.js:281-282`、`db.js:615-627`），卻沒有增加 `accounts.point`；因此欄名目前表示「計算值」而非實際 gained。數值仍是未確認 placeholder，可延後發錢，但需在啟用前裁定為「只記錄」或納入同一 transaction，避免帳與餘額語意分裂。
- **通過 — switch／封包失敗隔離。** `MATCH_WRITEBACK_MODE` 預設 disabled（`match-stats.js:65-86`）；DB 失敗由背景 IIFE 記 `MATCH-WRITEBACK-FAILED` 且不回拋至 EndGame 封包路徑（`:366-405`）。不過原子交易修正前不應啟用，且目前沒有重試／冪等 key。

## design §6 待審問題回答

1. **recordMatch 與全部 applyMatchAccumulation 必須同一 transaction：是。** 這是啟用前 must-fix，不接受逐玩家部分成功。
2. **`--dry-run` gate：可放寬。** 它在 `runMigration(...,{dryRun:true})` 只 SELECT；不必要求 `ALLOW_REAL_DB_WRITE`／備份確認。維持現狀只是過度保守，不是資料風險。
3. **is_test：裁定方向正確、目前實作不完整。** 三表照寫、零累加正確；必須以開場 participant snapshot 判定。
4. **participant CASCADE：技術推論正確，但產品資料保留政策未定。** 建議保留歷史，不採 CASCADE；請操作者裁定。
5. **Date binding：可用，但必須固定 timezone 並以真 MySQL round-trip 驗證。**
6. **win_team_rank=0／suspicious=false：可接受為 staged placeholder**，但不可宣稱已實作排名或 P7 判定。
7. **SQL 真實性：靜態核對與現有 schema 相容，但 fake pool 不證明 MySQL 可執行。** 先在 disposable/test schema 跑 migration、SHOW CREATE TABLE、rollback/failure integration test，再碰正式 DB。

## GO / NO-GO

**Step 1：GO。Step 2：NO-GO（先補 participant snapshot 與 host 戰鬥離場 abort marker）。Step 3 migration／啟用寫回：NO-GO。** Must-fix 是整場單一 transaction、UPDATE affectedRows 驗證、participant/is_test 開場快照；正式 migration 前另做 disposable MySQL 實跑與 schema post-check。真實 DB 本次只有 SELECT，未執行 migration 或任何寫入。

測試補充：migration 與 db.js 的 fake-pool 測試本次通過；marker/replay 測試因 worktree 唯讀而在建立 `logs/session-*.jsonl` 時 EROFS，未形成新的功能斷言結果。
