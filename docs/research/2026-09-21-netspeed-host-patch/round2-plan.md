**這一輪才是判定修補有沒有效的那一輪。** netspeed 的數字只是中間量。
**計畫的數字經 PM 確認之後才開跑。**

## ⚠️ 我對 PM 第 4 點（由房主開火）有不同意見

**PM 的設計**：房主開火；房主端數生成次數、加入者端數收到的 actor 數，差值＝遺失。

**我建議改成：加入者開火，用既有已驗證的計數法。** 三個理由：

1. **既有方法已經驗證過，而且已經量出同機環境的數字。**
   `next-test.md` 的量法（射手＝加入者，在**射手自己的** log 數
   `HitLoc===` 行數當分母、開火動畫當分子）在 2026-09-20 量到**同機雙開缺口 32–35%**。
   → **PM 第 1 點擔心的「A 組可能接近 0、沒有鑑別力」，用這個方法已經有先驗數據說不會。**
   改用房主開火就丟掉這個先驗，要重新賭一次。

2. **PM 的方法需要一個沒驗證過的計數管道。**
   「加入者端數收到的 actor 數量」——**我們不知道加入者的 log 會不會為
   「複寫過來的投射物」寫下同樣的動畫行**。`Now Animation Name : <武器> Fire`
   是本機生成時寫的；複寫生成會不會觸發同一行 ⬜。
   要用這個方法，得先花一輪驗證計數管道本身。

3. **兩個方向吃的是同一道閘門，所以換方向沒有額外好處。**
   機制是房主端 `ProcessRemoteFunction` 的廣播迴圈對**每條 connection** 查 `IsNetReady`
   （`0x105236a5`），門檻吃房主記的 `CurrentNetSpeed`——
   **那正是候選 1b 要改的值**。
   - 加入者開火 → 送給房主 → 房主 `ToAll` 廣播回來 → **卡在房主的預算**（已量到 32–35%）
   - 房主開火 → 房主廣播給加入者 → **一樣卡在房主的預算**
   兩者都測得到修補效果，但**只有前者有現成的計數法與先驗數字**。

**若 PM 仍堅持房主開火**，那就要先插一輪「驗證加入者端的計數管道」，這一輪的時程會拉長。

（操作者原本的觀察是「房主丟投射物、筆電那邊有時候看不到」——那是**症狀**的方向；
但我們要量的是**同一道閘門**，用哪一端開火不影響閘門，只影響計數的難易。）

## 實驗設計（以「加入者開火」為前提）

### 變數

**只有一個**：房主用的 `Engine.dll`。

| | A 組（基準） | B 組（修補） |
|---|---|---|
| 房主 `Engine.dll` | **stock**（`fc51fe1240ee34…`） | **候選 1b 修補後** |
| 加入者 | stock，兩組相同 | 同左 |
| 地圖／武器／開火方式／ini | 兩組完全相同 | 同左 |

### 每一輪的流程

1. 雙客戶端 C 段流程跑到進戰場（房主副本、加入者主安裝）
2. **加入者**開主控台打 `WeaponLog`（**toggle，開過就不要再打第二次**，
   每次重開客戶端都要重開一次）
3. 用 Pico 在**加入者**端按住開火鍵固定秒數，**每輪至少 100 次扣扳機**
4. 打完**關掉客戶端**才會完整 flush（log 4 KB 緩衝；且執行中檔案被獨佔鎖住讀不到）
5. 從加入者的 `data\System\run-*.log` 數兩個數字：
   - **分母**：`HitLoc=== >` 的行數（本機無條件寫，只有主武器有）
   - **分子**：`Now Animation Name : <武器>   Fire` 的行數
   - ⚠️ **分母絕對不要用 HUD 彈藥數**——雙臂武器一次扣兩發

### 控制項

- **同一張地圖、同一個時間點開始射擊**（PM 第 3 點）
- **要有網路負載**：用**有 bot 在交戰的 PvE 地圖**，不要空場景——
  成因是速率預算被吃光，空場景很可能量不到（PM 第 3 點）
- **武器**：投射物類（**砲類，不是機槍**；hitscan 不受影響），兩組同一把。
  ⚠️ 機體要挑主武器是砲類的——`RAVEN`（F1，輕量型）預設是機槍，**不適用**，
  開跑前要先確認選哪一台（見 `client-ui.md` 的八個槽位表）
- **失焦問題**：加入者視窗沒有焦點時畫面渲染可能降速。
  用 log 計數不受影響，**但要先確認加入者在失焦狀態下 log 仍照常寫**（PM 第 2 點）——
  這一項列為開跑前的前置檢查。

### 輪數與順序

**A、B、A、B、A、B 交錯**，各 3 輪（PM 第 5 點），避免時間順序造成偏差。
每組合計 ≥300 次扣扳機。
**報告列原始計數**（分子／分母），不要只給百分比。

## 成敗條件（我提的數字，待 PM 確認）

**先寫下來再開跑。**

| 判定 | 條件 | 依據 |
|---|---|---|
| **沒有鑑別力，停止** | A 組合計遺失率 **< 5%** | 這套配置量不到問題，繼續跑 B 組沒意義。備案：用筆電當加入者（log 在 `\\192.168.1.103\MROLog`），需要操作者晚上配合 |
| **修補有效** | A ≥ **15%** 且 B ≤ **A ÷ 3** 且 B 的絕對值 ≤ **10%**，且合併計數的 Fisher 精確檢定 **p < 0.01** | 先驗：同機雙開量到 32–35%，所以 A ≥ 15% 是保守門檻。n≈300／組時，33% vs 10% 的 p 遠小於 0.01 |
| **未定，加跑** | B 落在 `A÷3` 與 `A×0.8` 之間 | **不要硬下結論**（PM 第 6 點）。加跑 A/B 各 2 輪再判 |
| **修補無效** | B > A×0.8 | 記錄並回頭考慮房主端的其他路徑 |

**為什麼要求「B 的絕對值 ≤ 10%」而不只是比例**：如果 A 剛好只有 16%、B 是 5%，
比例上達標但**絕對遺失率仍然偏高**，那對實際遊玩體驗的改善有限。兩個條件都要過。

## 開跑前的前置檢查（都很便宜）

1. ⬜ **加入者視窗失焦時，log 是否照常寫**
2. ⬜ **挑一台主武器是砲類的機體**（`RAVEN` F1 是機槍，不適用）
3. ⬜ 確認 `WeaponLog` 目前的開關狀態：
   `grep 'WeaponLog=====> \(Started\|Ended\)'`——**不要重蹈 2026-09-20 開開關關的覆轍**
4. ⬜ 第 0、1 輪必須先過（DLL 能載入、房主 log 變成 `Client netspeed is 100000`）
