## 改了什麼

- `dispatch/map-info.sender.js`：新開關 `PVP_TEAM_ASSIGN_MODE`（預設 `'disabled'`），
  跟 `PVP_START_FLOW_MODE` 放同一個檔（單一來源），`module.exports` 一併輸出。
- `dispatch/gate.game.dispatch.js`：
  - import `PVP_TEAM_ASSIGN_MODE`。
  - 新函式 `resolvePvpTeamIndex(room, accountId)`：開關關閉、房間不存在、或
    `room.rawRoomType !== 2`（非 PvP）一律回 `0`（跟改動前一致）。開關開啟且 PvP 房時，
    依 `room.members`（`Map`，插入順序＝加入順序）分配 `i % 2`：
    房主（第一個成員）0（紅）、第二個 1（藍）、第三個 0……
  - **穩定性**：分配結果快取在 `room.pvpTeamAssignment_`（`Map<accountId, team>`），
    用 `room.pvpTeamAssignmentGen_` 對齊 `room.battleStartGen`（每次 `Game_Start_CN` 被接受時 +1，
    既有機制）。同一場戰鬥內所有 `Game_User_SN` 重送都拿同一個快取，不會因為重送或
    `room.members` 迭代順序而換隊；重開一場新戰鬥（`battleStartGen` 變了）才重算。
  - `sendGameUserSn`（單連線 fallback 路徑，`GAME_USER_SN_BROADCAST_MODE` 關閉或找不到
    tracked room 時用）：`teamIndex` 改用 `resolvePvpTeamIndex(rooms.getRoomByAccount(accountIndex), accountIndex)`。
  - `sendGameUserSnRoomBroadcast`（實際多人路徑，`GAME_USER_SN_BROADCAST_MODE` 預設 `'enabled'`，
    戰鬥開始時對全房每個成員送每個成員的 `Game_User_SN`）：`teamIndex` 改用
    `resolvePvpTeamIndex(currentRoom, currentSource.accountId)`——用迴圈裡每次重讀的
    `currentRoom`，跟這段既有的「每包重讀一次房間狀態」規則一致，不是外層那個可能過期的
    `room` 參數。
- `dispatch/room/room-game-user.sender.js`：硬規則 (a)（設計稿 §6 rule 2，`Game_User_SN
  rec+0x02` 只能是 0 或 1）寫成斷言，位置在 `sendGameUserBootstrap()` 開頭、緊接在
  `ctx` 解構之後、任何 DB 查詢或 buffer 配置之前。斷言失敗只 `console.error` 並 `return`
  （不送這一包，不丟例外、不讓伺服器掛掉）。
- 硬規則 (b)（`Grade_Info_SN 0x00510101` 必須是 0，非 0 時 `IsMeGM_BD()` 為真會讓加入者
  進觀戰）：找到全部 **7 個送出點**，全部已經是寫死的字面 `0`（目前沒有任何路徑會讓它變成
  非 0，所以這是防呆而不是修 bug），每處都改成「`gradeValue` 變數 + `if (gradeValue !== 0)`
  斷言，非 0 就 `console.error` 並跳過這次送出，是 0 才照原樣送」：
  - `dispatch/account.dispatch.js`：3 處（9211 登入：帳號不存在路徑、DB 錯誤 fallback 路徑、
    `sendAccountData()` 正常路徑）。
  - `dispatch/gamelogin.dispatch.js`：4 處（30907 登入：token 有效路徑、token 無效 fallback
    路徑、`handleChannelEnter` 前段一處、後段「Sent SN_GRADE_INFO: value=11」那處）。
  - `dispatch/community.dispatch.js`：1 處（`handleHangarOpen`，客戶端開 Hangar 時，
    這是離「加入者」情境最近的一個送出點——PvP 房 Enter_CQ 之後大廳的 Hangar Open
    流程會經過這裡）。

  全部 7 處寫死值本來就是 0，斷言永遠不會觸發（目前沒有任何呼叫方會傳非 0），加上斷言
  是為了未來有人改動時第一時間攔下來，而不是修正現有行為。

## 第 4 點：找到哪些地方有「隊伍」值（沒有改，只列）

除了 `Game_User_SN`（T1 改的那個），至少還有這些地方帶著隊伍/team 概念，
**這次都沒有動**：

1. **`SN_USER_DEFAULT 0x00220233` `+0x11`／body+0x13**（`dispatch/room/room-user.sender.js:125`，
   `teamIndex` 參數）——房內成員清單（房間 lobby UI 用），不是戰鬥用的 `Game_User_SN`。
   - 自己的那一筆：`ctx.teamIndex` 從 `dispatch/room.dispatch.js:1477`
     （`sendRoomState()`）硬寫 `0`；房主與加入者都一樣。
   - 別人的那一筆：`dispatch/room/room-user.sender.js:200`
     （`buildMemberUserCtx`）讀 `member.team || 0`，`member.team` 來自房間成員
     registry（`rooms.js` 的 `room.members`）。
2. **`member.team`（房間成員 registry 欄位，`rooms.js` `addMember()`）**——目前
   **三處呼叫方都硬寫 `team: 0`**：
   - `gate.game.dispatch.js:1351`（`CQ_CREATE`，房主建房時把自己加進房間）。
   - `gate.game.dispatch.js:2083`（`Enter_CQ`，加入者加入房間，就是這篇註解
     「PvE all-red…PvP team assignment is M4」的那一處）。
   - `gate.game.dispatch.js:2202`（另一個 `buildMemberUserCtx({ ..., team: 0, ... })`
     呼叫，也是房內成員清單相關）。
   - 這個欄位同時餵給**房內文字聊天的隊伍過濾**（`case 0x00220503` Team 頻道，
     `senderTeam`／`member.team !== senderTeam` 比對，`gate.game.dispatch.js:2606-2612`）
     ——房間內聊天，不是戰鬥內聊天（戰鬥內 `0x00220507`／`0x00220509` 只是回聲，
     沒有隊伍過濾，不受影響）。
   - 也餵給 `dispatch/room/match-stats.js:146`（`team: member.team || 0`，比賽紀錄
     metadata）——這是 T2 之後才會用到的東西，這次沒有動。
3. **`Room_Default_SN`（房間本身封包）body+0x10／+0x12**（`dispatch/room/room-state.sender.js:11-12`，
   `ROOM_RED_TEAM_INDEX=0`／`ROOM_BLUE_TEAM_INDEX=1`）——這是**房間層級**的紅/藍隊伍索引
   常數（跟 `Game_Info_SN` 的 `+0x04`/`+0x06` 是同一組值），**不是逐成員**的隊伍，
   固定 0/1 本身沒有跟誰對不上的問題。

### 會不會對不上

**會**，但只在「進房到開戰之前」這段時間：`member.team`（進而 `SN_USER_DEFAULT` 的
per-member team）在這次改動後**仍然全部固定 0**，房間 lobby 的成員清單／隊伍 UI
（如果客戶端真的用這個欄位畫紅藍分隊介面的話）**看起來會兩個人都在紅隊**；
但**戰鬥一開始，`Game_User_SN`（本次改的那個）會正確送出 0／1**，機體實際落地哪一隊
（`Game_User_Team_Get` 比對的陣列）會照 T1 的分配。也就是說：**房間 lobby 畫面的
隊伍顯示，跟開戰後戰場裡的實際分隊，會不一致**——如果客戶端在 lobby 就用
`SN_USER_DEFAULT` 的 team 欄位畫紅藍隊，玩家會看到自己在 lobby 顯示紅隊、
一開戰卻可能被分到藍隊。

這跟設計稿 U4（`Team_Change_All_SN`，房內換隊，本輪明確排除）是同一塊——
真正的原廠流程可能本來就是「lobby 先全部丟紅隊、玩家自己用換隊 UI 挑邊」，
如果是這樣，lobby 全紅其實是正確的初始狀態，不是 bug。**這件事在 2 人實跑
之前無法判斷**，先列出來，不在本輪擴大範圍去改。

## 2 人實跑最可能看到的異常（預測，未驗證）

1. **房間 lobby 畫面兩人都顯示紅隊**（見上「會不會對不上」），開戰後才分成紅/藍——
   如果客戶端真的用 `SN_USER_DEFAULT` 畫 lobby 隊伍 UI 的話會很顯眼，但**可能是正確的
   原廠行為**（換隊本來就要玩家自己點）。
2. **`Death_SN` 對加入者的安全性**（設計稿 §5，PM 已經裁決可以送，但這是第一次真的有
   兩個不同隊伍的玩家在打架，不是單純廣播）——設計稿明講「第一次 2 人實跑唯一要盯的：
   加入者有沒有崩潰」，T1 這個分隊改動是讓這件事第一次被真正考驗的原因，值得特別注意。
3. `resolvePvpTeamIndex` 用 `room.members` 的**當前**插入順序，如果两人幾乎同時
   Enter_CQ、`room.members.set()` 的順序跟「螢幕上看到的加入順序」不一致（極端 race），
   紅藍可能跟直覺的「先建房的人是紅隊」對不上——機率低，但沒有實測過。
4. 斷言本身：如果任何地方的 `teamIndex` 算出 0/1 以外的值（目前程式邏輯保證不會，
   因為只用 `i % 2`），`room-game-user.sender.js` 會直接跳過那個成員的 `Game_User_SN`，
   結果會很像「這個人一開戰就沒有機體」——如果實跑看到這個症狀，先查 log 裡的
   `!! Game_User_SN assertion failed` 那行。
