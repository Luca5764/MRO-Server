## 先講一件跟契約前提不符的事（🟡，需要主力判斷）

契約第 3 層堵點（`campaignStarted_` 擋掉開戰後四個步驟，
`gate.game.dispatch.js:792,813,836,858` 的四個 return 閘門）描述的是**已經不是
live 路徑的舊碼**。`SERVER_DRIVEN_START_MODE`（同檔 `:182`，硬編碼 `'enabled'`，
`docs/reference/switch-audit.md:35` 標「D 暫不動」）在 case `0x00222103` 內於
line ~1854（改動前行號）就 `return true`，**之後那四個 gate 函式與它們的呼叫點
（原 1870/1876-1884）全部在這個 return 之後，現在的預設組態下永遠不會被執行**。
現在真正 live 的戰鬥開始序列，是 `SERVER_DRIVEN_START_MODE === 'enabled'` 那個
分支自己（原 1702-1844），它**不看 `campaignStarted_` 做任何 gating**——不論房型，
Game_Wait_SN／Game_User_SN／Game_Info_SN／Ready_Host 全部無條件送出。
`campaignStarted_` 在 live 路徑裡只被**寫入**（原 1741/1748），沒有任何 live 讀取
在用它做判斷。

同時，`room.dispatch.js` 的另一個 `campaignStarted_` 賦值點（case `0x00240301`，
標注「Game Start CN」）也是死碼：`0x00240301` 實際是 `ZDispatchHangar::
Item_Expiration_SN`（server→client，見 `docs/client-dispatch-map.md:161,497`、
`docs/reference/multiplayer-audit.md:29`），客戶端從不送這個當 CN。真正的
Game_Start_CN 是 `0x00222103`（`gate.game.dispatch.js`）。

**結論**：契約要求的「四個 return 閘門改看 `battleStartSequenceArmed_`」本身無害
但目前**不影響任何 live 行為**（開關開或關，這四個 gate 都不會被執行到）。真正
在 live 路徑上會擋住 PvP 開戰的，是契約裡的第 1 層（`MapInfo_SN` 沒送 PvP 地圖 id）
與第 2 層（`campaignMapCacheKey_` 無條件退回 9001）——這兩層我已經照契約修好，
而且**確認是 live 路徑會用到的**（`sendGameInfoSn`／`sendReadyHostSn` 都讀
`client.campaignMapCacheKey_`，兩者都在 `SERVER_DRIVEN_START_MODE` 分支內被呼叫）。
沒有停下來等回覆——這個發現不影響「照契約做安全、可關閉的改動」這件事本身，
只影響「這次改動對 live PvP 有多大幫助」的判斷，寫在這裡讓主力決定要不要進一步
動 `SERVER_DRIVEN_START_MODE` 那個分支（**這次沒有動，那是它自己的『D 暫不動』
清單成員，不在本契約範圍內）。

## 兩個旗標最後叫什麼

- **`isCampaignRoom_` 的角色**：程式碼裡本來就已經有 `client.isTrueCampaign_`
  在做這件事（`rawRoomType_===1 || gameMode_===4||5`，CQ_CREATE 算好後存的），
  全 repo 一致地被當「這是不是真戰役房」用（`campaignMapCacheKey_` 的預設值、
  `sendCampaignBootstrap` 等都已經看它，不是看 `campaignStarted_`）。契約允許
  「或同義的清楚名字」，所以**沒有新增欄位，直接沿用 `isTrueCampaign_`**，避免
  改一個已經在全 repo 好幾個檔案裡被正確使用的欄位名，徒增風險。
- **`battleStartSequenceArmed_`**：`campaignStarted_` 整個重新命名成這個名字，
  **沒有留相容別名**（讀取端只有 `dispatch/`＋`session.js`＋`packetlog.js`＋
  `test/room-battle-start-broadcast.js`，全部一次改完，沒有外部消費者需要舊名）。
  三個賦值點（`gate.game.dispatch.js` 兩處 live/一處死碼、`room.dispatch.js`
  一處死碼）都加了同一個 OR 子句：
  `|| (PVP_START_FLOW_MODE === 'enabled' && Number(rawRoomType_) === 2)`
  （死碼那處故意不加，維持純重新命名，見檔內註解）。

## 開關

`PVP_START_FLOW_MODE`，定義在 `dispatch/map-info.sender.js`（依賴圖最乾淨的葉檔案，
零 require，`gate.game.dispatch.js` 反過來 require 它），**預設 `'disabled'`**。
`enabled` 時同時影響：
1. `resolveRealMapIds()`（map-info.sender.js）：`MAP_INFO_REAL_IDS` 併入
   `MAP_IDS_PVP`（8 個 TDM id，跟 `room.dispatch.js:180` 同一組值，註解說明為何
   複製一份而非 cross-require，比照 `CAMPAIGN_MAP_ALL_HINTS` 既有先例）。
2. `gate.game.dispatch.js` CQ_CREATE handler：`campaignMapCacheKey_` 的預設值，
   PvP 房（`rawRoomType===2`）改用 `MAP_IDS_PVP`/`MAP_ID_DEFAULT_PVP`（1011），
   而不是無條件 9001。
3. 上一節提到的 `battleStartSequenceArmed_` 三個 OR 子句。

## Golden replay：怎麼做的與結果

`test/replay-golden.js` 是既有的離線比對工具（無 TCP、無真實 MySQL），但它的
`pve-full-match` 樣本在**改動前**就已經對不上自己的 `expected.jsonl`
（`send #21`，op `0x00210113`，offset `0x12`，兩次重跑同一個錯誤值，是既有樹上
的既存問題，跟本次改動無關，未嘗試修——不在契約範圍）。因為它一發現不符就
不繼續比對後面 8000+ 筆，不能直接拿來當「開戰序列有沒有變」的證據。

改用同一份工具內部的 `replaySample()` 邏輯（fixture DB／fake timers／module-cache
重置，完全比照 `replay-golden.js`，未修改該檔案本身）另外接一支 scratch dump
腳本（`/tmp/dump_sent.js`，不在 repo 裡），把 `client._sent` 整包序列化：

```
node /tmp/dump_sent.js "<worktree>/Metal Rage Online Server" <sample> before-<sample>.jsonl   # 改動前
# ...實作...
node /tmp/dump_sent.js "<worktree>/Metal Rage Online Server" <sample> after-<sample>.jsonl    # 改動後，開關仍 disabled
diff before-<sample>.jsonl after-<sample>.jsonl
```

四個既有 golden 樣本（`login-dispatch` 14 包、`login-room-game` 51 包、
`login-room-shop-buy` 364 包、`pve-full-match` 8384 包）**全部 `diff` 完全一致**
（`IDENTICAL`），開關維持預設 `disabled`。另外跑過完整 `test/*.js`：除了本來就需要
真 MySQL、這個 sandbox 本來就會 `MODULE_NOT_FOUND` 的既有檔案
（`exception-guard.js`／`item-equips.js`／`match-writeback.js`／
`p1b-default-items.js`／`p3-db-recordmatch.js`，跟本次改動無關，改動前即如此）
與上面提到的既有 `pve-full-match` 失敗外，全部 PASS，包含改過的
`test/room-battle-start-broadcast.js`。

**開關臨時打開的健檢**（改完立刻改回 `disabled`，未進 commit）：

`count===12` 的既有測試因此如預期失敗（那個測試本來就沒設計來涵蓋這個新開關，

## 沒做完或需要主力決定的事

1. **最重要**：如上所述，`SERVER_DRIVEN_START_MODE` 的 live 分支目前完全不讀
   `battleStartSequenceArmed_`，所以光開 `PVP_START_FLOW_MODE` 不會改變 live
   行為的「第三層」——真正會生效的只有第 1、2 層（地圖清單、`campaignMapCacheKey_`
   預設值）。如果目標是「打開開關就能讓 PvP 房打到底」，`SERVER_DRIVEN_START_MODE`
   那個分支本身需要額外決定要不要讀這個旗標——這是「D 暫不動」清單成員，我沒有
   自己動它，留給主力判斷。
2. **開關打開後最可能先失敗的一步（我的判斷）**：不是 `campaignStarted_`
   閘門（反正它現在不擋 live 路徑），而是 **`Game_User_SN` 的 team 欄位**
   （`pvp-start-gap.md` Q5）——PvP 房兩個玩家的 `rec+0x02` 目前雙方都寫死 0，
   `Game_User_Team_Get` 因此把所有人判成同一隊；`Game_Info_SN` 的
   Red/Blue TeamIndex（0/1）本身沒問題，但沒有任何玩家的 per-player teamIndex
   被設成 1，這件事在契約裡被明確排除（「不要動 `Game_User_SN` 的 team 欄位」），
   所以就算地圖對了、開戰序列跑完，兩個玩家大概率會被判在同一隊——這是下一個
   契約該處理的東西，不是這次的範圍。其次可能失敗的是 `body[0]=6` 那個第三種
   房型（見下）完全沒有分流，會落到錯誤的 `maxPlayers` 計算。
3. **待辦、不順手做**（契約明確排除）：`body[0]=6`（internal RoomType 4）那個
   新發現的房型——`isCampaignLike`／`maxPlayers` 都沒有對應分流，
   `roomNumberValue` 被誤當成人數上限用（其實是 `QuickTitleIndex`），詳見
   `pvp-start-gap.md` Q6 末段。
4. `test/map-info-game-login.js` 如果之後真的要把 `PVP_START_FLOW_MODE` 打開，
   需要補一個新案例（12→20 筆），現有的 `count===12` 斷言會擋住；這次沒有動它，
   因為開關預設關閉，該測試現有斷言仍然正確。
