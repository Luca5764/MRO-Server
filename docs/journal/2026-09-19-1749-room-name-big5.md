# ROOMNAME-BIG5：房間名 Big5 位元組不失真（中階，🟡，未經跨公司審查）

範圍：`AGENTS.md` 契約任務。實作行為藏在預設關閉的開關後面，唯讀部分（客戶端名稱長度限制）附在
最後。分支 `flash-wip-roomname`，worktree `~/mro-wt/roomname`。

## 背景

[LOG] `session-20260919-122616.jsonl` ms 4742361：Create_CQ 0x00220201 body+14 送出
`b4fab8d5a9d0b6a1`（Big5 的「測試房間」），ms 4755523 則是 ASCII `"test room"`——證實房名欄位
（body+14..38，25 bytes）是 client 端 ANSI（cp950/Big5）編碼，不是 UTF-16LE。

既有程式：
- `gate.game.dispatch.js`（Create_CQ handler）用 `.toString('ascii')` 解析這段 bytes——Node 的
  `'ascii'` 是 7-bit，會把 Big5 每個高位元組的最高位遮掉，直接讀出亂碼字串。
- `dispatch/room/room-string.js` 的 `toSafeAscii()` 把非 ASCII 字元換成 `'?'`，寫回
  `Room_Name_SN 0x0022021A` 時整段變成問號。
- [OBS] 操作者回報中文房名顯示亂碼；另外 `session-20260919-170919.jsonl` ms 1817495 的
  「鐵影特攻一戰？！」（8 個全形字＝16 bytes Big5）送出**空房名**，伺服器回退用暱稱頂替。

## 做了什麼

新開關 `ROOM_NAME_RAW_BYTES_MODE`（`dispatch/room/room-string.js`，`let` + accessor，同
`room-map.sender.js` 的 `mapAllSingleEntryMode` 寫法），預設 `'disabled'`：

- `decodeAnsiBytes(buffer)`：開關關閉時等同舊的 `.toString('ascii')`；開啟時改用
  `'latin1'`（1 byte ↔ 1 JS char，不會遮位元），讓 Create_CQ 的房名/密碼原始位元組完整保留。
  `gate.game.dispatch.js` 的兩個解析點（body+14 房名、body+40 密碼）都改呼叫它。
- `writeAnsiStringField()`（`Room_Name_SN` 用）：開啟時改用 `'latin1'` 寫回，保留欄位長度
  （`fieldSize`）與結尾 NUL 的既有邏輯（`buffer.fill(0, ...)` 先清零，只是多寫的位元組數改算
  latin1 位元組數而非 `toSafeAscii()` 夾住的 25 字元）。
- 新的 `toRoomNameWireBytes(value, maxBytes)`：`Room_List_SN`（大廳清單，`room-list.sender.js`）
  的房名欄位是長度前綴（無固定寬度），沒有 `writeAnsiStringField` 可用，另外包一個回傳
  `{text, encoding}` 的版本給它用。
- `gate.game.dispatch.js` 裡 Create_SA 0x00220202 也會把房名寫回 body+0x0E（25 bytes 固定欄
  位）——這是另一個獨立的房名回顯點，原本用 `.write(roomName+'\0', ..., 'ascii')`。改成開關開
  啟時 `'latin1'`＋latin1 位元組長度；關閉時完全沿用舊碼路徑（含舊碼本來就用 `Buffer.byteLength`
  預設 utf8 算長度、再用 `'ascii'` 寫入的既有不一致，沒有動它，避免同時改兩個變數）。
- log 可讀性：`decodeBig5ForLog(value)` 用 `new TextDecoder('big5', {fatal:true})` 把儲存的
  latin1 字串試著解回中文，只在開關開啟時呼叫、解碼失敗回傳 `null`（不印東西），不影響既有的
  hex dump。確認過這台 Node（24.21.0）內建完整 ICU，`new TextDecoder('big5')` 可用
  [TEST]：把 `b4fab8d5a9d0b6a1` 解回「測試房間」。加在 `gate.game.dispatch.js` 的建房 log 與
  `room-state.sender.js` 的 `Room_Name_SN` 送出 log。

**密碼**：Create_CQ 的密碼（body+40, ANSI）用同一個 `decodeAnsiBytes()`；沒有找到任何地方會把
密碼文字回顯給 client（只送一個 has-password bool），所以只改了存值路徑。附帶發現一個既有、
與本題無關的不一致：Enter_CQ 0x00220231 的密碼欄位是 UTF-16LE（`gate.game.dispatch.js:1809`
註解已標明，[DLL] 0x107e5e61），跟 Create_CQ 的 ANSI 密碼不同編碼——這代表非 ASCII 密碼現在
（不管這個開關開不開）本來就无法正確比對成功，這題沒有處理，留給下一輪。

**沒找到的東西**：全專案 grep 沒有 Room_Option／房間改名 handler（`grep -rn "Rename\|Room_Option"
dispatch/`只命中既有的 Room_Option_Change 0x00220215/0x00220216，跟房名無關，是隊伍平衡/中途
加入設定）。房間建立後似乎沒有改名功能，本題涵蓋的回顯點就是 `Room_Name_SN`／`Room_List_SN`／
`Create_SA` 這三個。

`room.dispatch.js:1514` 的 `(client.roomName_ || ...).slice(0, 25)`（房主自己送 `Room_Default_SN`
前的房名來源）沒有動——這是既有的字元數上限，不是編碼 bug，且跟 Q2 的唯讀調查結果（25 是
client 端本來就有的欄位大小）一致，不在本題「編碼回顯」範圍內。

## 唯讀調查：Q2 房名長度限制

`~/mro-decrypted/src/ZGameMainMenu/ZPopup_CreateRoom.uc`：`CreateRoom()`（368-506 行）只檢查
`RoomName == ""`（空字串擋掉），完全沒有 `MaxLength`／字元數檢查就直接呼叫
`Lobby_Room_Create(RoomType, RoomName, RoomPassword, ...)`。`GUIEditBox.uc` 本身也沒有
`MaxLength` 欄位——但這批反編譯出來的 `.uc` 全部**沒有 `defaultproperties` 區塊**（專案已知的
反編譯系統性缺陷，見 `docs/research/2026-09-18-room-setting/notes.md`），所以不能排除
editbox 有 native 端設定的字數上限沒有反映在原始碼裡。

反查 native 端（`tools/disasm.py`）：`execLobby_Room_Create`（`0x10705367`）是個 thunk，
真正的參數解析在 `0x10718740`。這段是 UnrealScript native 呼叫的標準「從 bytecode frame 逐一
取參數」樣板（透過 `[0x1091b850]` 這類函式指標表按屬性型別分派），把 RoomName／RoomPassword
兩個 FString 參數轉成暫存值後，在 `0x10718924` 呼叫 `0x10705925`（thunk）→
`0x107e5b60`（已有舊反編譯 `docs/research/2026-09-17-fire-gate/Lobby_Create_CQ.c`）組出
CQ_CREATE 封包。

**卡住的地方**：讀完 `FUN_107e5b60` 全部 81 行反編譯，這個函式清零 0x400 bytes 封包緩衝、寫
opcode／MaxUser／MapIndex 等數值欄位，**完全沒有任何一行碰 body+14 或 body+40**——RoomName／
RoomPassword 的 FString→ANSI 轉換與複製顯然發生在更早的 `0x10718740` thunk 內，透過
`call dword ptr [0x1091b894]`／`call dword ptr [0x1091b84c]`（`0x107188d7`-`0x1071891f`
一段）完成，但這兩個位址是執行期才填值的函式指標表項目（UnrealScript native property
accessor，跟 `0x1091b850` 同類），靜態反組譯無法解析它們實際指向哪個函式——需要動態除錯
（附加除錯器單步，或至少一個能列出這張表在特定執行時刻內容的方法）才能確認。

**結論：⬜ 未能從靜態反組譯確認長度限制規則**（既沒找到 truncate 也沒找到 reject 的明確位元組
邊界）。唯一能確定的觀察：16-byte Big5 房名（8 個全形字）送出空字串，跟「25-byte 欄位截斷」
這個最簡單的假設矛盾（16 < 25，簡單截斷不該把整段清空）；比較可能是 client 端某個更早的字元數
或 IME 檢查把整個字串丟棄，而不是位元組級的截斷——但這只是 🟡 推測，不是確認。建議下一步：
用調試器對 `0x1091b894`/`0x1091b84c` 下中斷點，或找 `Lobby_Room_Create` 的另一個呼叫路徑
（例如 log 裡 client 是否在送出前就跳出提示）。

## 追加：Name_Change_CQ 0x00220218 沒有 handler（PM 現場測試發現，🟡，未經跨公司審查）

範圍追加：PM 現場測試房間設定變更對話框時，按 OK 送出 `Name_Change_CQ 0x00220218`（25 bytes
ANSI 房名，無其他欄位）[LOG] `logs/session-20260919-*.jsonl` ms 2365887 conn6，伺服器沒有
handler，走到 `default:` 分支——因為 `0x00220218` 是偶數，既有的「奇數 CQ 自動回 type+1」機制
（`gate.game.dispatch.js` 尾端 `default:` 分支 `type % 2 === 1`）完全不會套用到它，於是**什麼都
沒回**，client 卡在讀取畫面等 `Name_Change_SA 0x00220219` 永遠等不到。

**反組譯找到的 SA opcode 配對**：`execRoom_Name_Change@UZNetwork_DJ`（`0x1070960b`）thunk 到
CQ 建構函式，該函式把房名截到 `0x19`（25）字元後呼叫 `Send(buffer, 0x220219)`——`Send()` 第二
個參數是**預期回覆的 opcode**（跟 `gate.game.dispatch.js` 既有註解「`ZDispatchLobby::Create_CQ`
送 `0x220201`、`Send(...,0x220202)`」是同一個慣例，不是封包大小），證實 SA 是 `0x00220219`、
不是常見的 `CQ+1`。

**SA body 佈局（🟡 部分反組譯、部分未確認）**：反查 `Name_Change_SA@ZDispatchRoom`
（`0x10708a6c`）thunk → 真正的 client 端接收處理在 `0x107eb160`。確認的部分：
- 成功條件是 `word[+0x10]==0 && dword[+0x12]==0`——跟這個 codebase 到處都在用的「標準 6-byte
  OK header（u16 Result + u32 ErrorCode）」慣例一致（`0x107eb216`/`0x107eb221` 兩個
  `cmp`/`jne`）。
- 成功時（`0x107eb2a8`-`0x107eb2bf`）client 會用 `body+0x10` 當起點、上限 `0x19`（25，跟 CQ
  送出端截斷長度相同）組出 FString，寫回自己的房名欄位——代表 SA **確實有帶新房名**，不是
  單純的 0/0 ack。
- **沒確認的部分**：header（6 bytes）跟 name 欄位（body+0x10 起）中間的 10 bytes（body+0x06
  到 +0x0F）沒能從靜態反組譯確認內容——esi（Format 包裝物件）跟 ebx（PAD 原始 body 指標）
  是否對齊到同一份 buffer 的同一個偏移，需要動態除錯才能百分之百排除。目前實作直接假設
  body+0x10 就是 raw body 的偏移 0x10（body 總長 `0x10+0x19=0x29`＝41 bytes），中間 10 bytes
  留 0（`getExactMessageBuffer` 預設清零）。

**實作**（`ROOM_JOIN_MODE` 既有開關控制，關閉時完全沿用舊的「無回應」行為）：
- `gate.game.dispatch.js` 新增 `case CQ_ROOM_NAME_CHANGE`（`0x00220218`）：開關關閉時
  `packetlog.fallback(..., null); return true;`——跟原本落到 `default:` 分支時的行為逐位元組
  相同（`type%2===0` 本來就不會自動回覆）。
- 開關開啟時：解析 25-byte 房名（`decodeAnsiBytes()`，跟 Create_CQ 共用同一個
  `ROOM_NAME_RAW_BYTES_MODE` 開關）；只接受目前房間的房主（`room.hostAccountId===accountId`）、
  空字串拒絕；成功時更新 `room.name`／`client.roomName_`，回 `Name_Change_SA`（成功帶新房名於
  body+0x10，失敗只回 1/1 header）；對房內每個成員（含房主自己）送
  `Room_Name_SN 0x0022021A`（新拆出的 `sendRoomNameOnly()`，見下）；`lobbyRoomListMode` 開啟時
  另外對大廳廣播 `Room_List_SN`（`UpdateType=2` 部分更新，語意上跟 D1-4 CQ_CREATE 用 1／Leave
  用 3 一致）。
- 把 `room-state.sender.js` 裡 `sendRoomStatePackets()` 內建的 `Room_Name_SN` 發送邏輯抽成獨立
  `sendRoomNameOnly(client, roomName, getExactMessageBuffer)`（逐位元組不變，純函式抽取），
  改名 handler 跟原本的整包房間狀態發送都呼叫同一份程式碼。
