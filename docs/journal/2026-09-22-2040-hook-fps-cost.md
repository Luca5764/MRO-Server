# Frida 掛鉤的 FPS 代價：砍一半，而且收窄不回來

BRIDGE-SPIKE，PM 2026-09-22 定的門檻：**掛鉤前後 FPS 差 <5% 才能當主要數字**。
劇本 `experiments/bridge-fps-compare.json`（單人 PvE，開火 6 發後於戰鬥中讀 `stat fps`）。

## 四組結果

| 組 | 掛點 / onEnter | cur / **avg** FPS | 相對基準 | 結果 |
|---|---|---|---|---|
| 0 基準 | **無 Frida**（gadget dll 改名移開） | 567 / **547** | — | PASS |
| 1 現行 `bridge-fire.js` | `+0x2234b0`（函式開頭）／解名字＋普查 | 215 / **276** | **−50%** | PASS |
| 2 方案 B `bridge-fire-narrow.js` | 同位置／**只剩兩次指標比對** | 310 / **271** | **−50%** | PASS |
| 3 方案 C `bridge-fire-late.js` | `+0x223564`（`FUNC_Net` 判斷之後） | — | — | **FAIL，客戶端 GPF** |

## 結論一：成本在 trampoline 的觸發次數，不在 onEnter 做了什麼

**把 `onEnter` 從「FName 解析 ＋ 普查」砍到「null 檢查＋計數＋兩次指標比對」，
FPS 一點都沒救回來**（276 → 271，雜訊範圍內）。

這推翻了一個很自然的直覺（「hook 裡少做事就會比較快」）。每秒攔十幾萬次時，
**光是進出 hook 的固定開銷就吃掉一半 FPS**。
→ 以後設計任何 Frida 掛鉤，**先問「會被觸發幾次」，不要先想「裡面做什麼」。**

## 結論二：方案 C 把客戶端弄掛了

`0x10523564`（`FUNC_Net` 檢查之後、廣播/單一連線分岔之前）掛上去之後：
- hook **有掛上**（log 印出位址，無 attach 錯誤）
- 但 `calls=0` **從頭到尾沒觸發過**
- 客戶端在 `ClientTravel` → `LoadMap` → `SpawnPlayActor` → `SpawnActor` 時 **GPF**，
  堆疊正好經過 `UObject::ProcessEvent`
  （[OBS] 操作者貼回完整堆疊，存於 `research/2026-09-22-bridge-spike/late-hook-crash.txt`）

前三組跑**同一支劇本**都沒事，唯一的變數是掛點 → 🟡 **高度懷疑是掛點造成**，
但**只發生一次、沒有重現**（⬜）。

🟡 可能的機制（未驗證）：Frida 要在掛點寫入跳轉，需要 ≥5 bytes，
而 `0x10523564` 起是 `mov edx,[edi]`(2) + `mov ecx,edi`(2) + `call [edx+0x1d4]`(6)，
必須搬走整整 10 bytes。**若有別處的跳轉落在 `0x10523566` 或 `0x10523568`**，
就會跳進 Frida 的 trampoline 中間 → 崩潰。函式開頭（組 1／2）沒這個問題，
因為那裡本來就是所有呼叫的入口。
→ 要救的話得先做完整 xref 掃描確認沒有跳轉落在被覆蓋的範圍內。**本輪不做。**

## 對 PM 門檻的判定

**沒有任何一組通過 <5%。** 所以：
- ❌ **Frida 計數不能當主要數字**，PM 的通則（要跟舊數字比的量測一律用 log 計數）維持。
- ✅ Frida 仍然可以用在**不依賴 FPS 的量測**（場景追蹤、封包內容、狀態讀取），
  以及**掛鉤前後都掛著**的 A/B（兩邊條件相同就可比）。
- ⬜ 「數 `IsNetReady` 回 false 的丟棄次數」（PM 已預先核准的下一步）**現在做不了**——
  那個位址 `0x105236ad` 在函式中段，跟崩潰的 `0x10523564` 是同一類風險。
  要做得先解決中段掛點的安全性問題。

## 順帶確立的事實

**ASLR 是開著的。** 這一輪 log 印出 `Engine.dll base=0x3050000`（偏好基底是 `0x10300000`），
先前 `ZNetwork.dll` 也落在 `0xcda0000`。
→ **任何寫死 VA 的程式都會錯**，一律用 `Process.findModuleByName()` 再加 offset。
我們的腳本都是這樣寫的，但這條要記著。

## 量測方法的缺陷（已開契約）

FPS 用 `stat fps` 的畫面 overlay ＋ 截圖判讀，**只有單一瞬間、看不到 frame-time 分布**。
而且截圖檔名會被下一輪覆蓋——**基準組那張已經被蓋掉，數字有記錄但原圖沒留**（我的疏失）。
`FPS-PRESENTMON` 契約（`docs/backlog.md`）要把這件事換成外部工具自動記錄。
