# 「換地圖會斷線重連」其實是已修好的切封包 bug

更正 `2026-09-19-0215-no-reconnect-during-battle.md` 裡的疑問。

- [LOG] `session-20260917-131036.jsonl` 的 9 次 30907 重連中，有 8 次（conn2/4/6/8/10/12/16/18，關閉位置在 131、2097、2211、2355、2477、2588、16311、16650 行）斷線前的最後一組都是：收到 `Death_CN 0x00230123` → 送出 `Death_SN 0x00230124` → 伺服器關閉連線；接著客戶端送出新的 `Login_Again_CQ 0x00110124` 自動重連。
- [GIT] 原因是 `client.js` 把 frame 長度補齊到 16 的倍數才消耗，同一個 TCP chunk 裡黏著的下一個封包就被吃掉開頭幾個 byte → 伺服器斷線（`journal/2026-09-17-13` 的測試 O）。已由 `6aa39ba`（2026-09-17 19:35）修好，131036 那場全部發生在修好之前。
- [LOG] `session-20260919-002245.jsonl`：同樣的 Death_CN／Death_SN 組合出現 269 次，都沒有斷線。
- 結論（🟡，未經跨公司審查）：**換地圖本身不會重連。** `Login_Again_CQ` 是每條 30907 連線一開始的標準握手。AGENTS.md 陷阱表的那一列已改寫。
- 還沒解釋的兩次（修好之後）：`session-20260917-220519.jsonl` 約 131 行（斷線前是 fallback 的 `0x00220114`）、`session-20260918-205012.jsonl` 約 9262 行 ⬜。
- **對 D1 第 0 步實測的影響：** 伺服器主動斷線後，客戶端會用它存起來的 away-certify 值自動重連（131036 的 8 次都是這樣）。所以實測改成由伺服器主動斷掉某個帳號的 30907 連線（console 指令），看它重連時帶的 (accountId, key) 是否不變、是否被認成同一個帳號。不需要請操作者重開客戶端。

## 更正（2026-09-19，PM 審查後，高階自行核對）

- **「伺服器主動斷線後客戶端會自動重連」是錯的。** [LOG] `session-20260917-131036.jsonl` 的連線順序（高階重跑）：每一條 30907 連線（conn 2/4/…/18）前面都緊接著一條新的 9211 登入（conn 1/3/…/17），兩次登入之間隔 214–8674 秒。這是操作者手動重新登入，不是自動重連。PM 另外掃了 74 份 log：78 次 `Login_Again_CQ`，前 5 秒內全部都有 Gate `Leave_SA 0x00220132`，沒有例外。
- 所以 `/drop` 不能拿來驗 D1 第 0 步（重新登入會經過 Gate，拿到新的 key）。改成保留給 D1 第 5 步測「有人斷線」用；第一次使用時，要留下被斷線那台的截圖和 MetalRage.log（畫面行為 ⬜）。
- 切封包 bug 造成誤斷線這部分仍然成立。只是斷線之後是人重新登入，不是客戶端自動連回。AGENTS.md 陷阱表已再次改寫。
