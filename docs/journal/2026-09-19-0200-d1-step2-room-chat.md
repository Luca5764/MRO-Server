# D1 step 2：rooms.js 廣播輔助＋房間聊天

日期：2026-09-19
狀態：🟡 待審（中階實作，未經跨公司審查）
分支：`flash-wip-d1s2`（worktree `~/mro-wt/d1s2`），依 `docs/backlog.md` D1-2 契約
依據：`docs/design/d1-multiplayer-room.md` §3、§5、§6 step 2；`docs/client-dispatch-map.md`；
`test/README.md`「login-room-game」樣本說明

## 做了什麼

1. **`rooms.js` 新增 `sendAll(roomId, build)`／`sendOthers(roomId, exceptAccountId, build)`**。
   兩者都走 `room.members.values()`，跳過 `member.client === null`（斷線中，design §4），
   對每個成員各自呼叫一次 `build(member.client)` 並 `member.client.send(msg)`。`build`
   每次呼叫都要回傳全新的 buffer——`client.getMessageBuffer` 用的是該連線自己的
   `sndbuf_`（`client.js` 註解「only one message can be acquired at a time」），不能把同一個
   buffer 物件塞給兩個不同連線的 `.send()`。這次的呼叫端一律用
   `gate.game.dispatch.js` 既有的模組層級 `getExactMessageBuffer(type, size)`（`Buffer.alloc`
   全新配置，跟 client 連線無關），天生滿足這個限制。

2. **`dispatch/gate.game.dispatch.js` 新增 `0x00220505`（Chat_Room_All）／`0x00220503`
   （Chat_Room_Team）case**，觸發動作是客戶端在房間聊天框按 Enter（不是房間外的大廳
   `0x00220501`、也不是戰鬥中的 `0x00220507／0x00220509`）。先查
   `rooms.getRoomByAccount(accountId)`：
   - 帳號不在任何房間（或開關關閉）：維持原本 default 分支行為，回 ACK
     （`type+1`＝`0x00220506`／`0x00220504`，6 bytes）。
   - **在房間裡**：`0x00220505` 用 `rooms.sendAll(room.id, build)` 原樣廣播整個房間
     （含自己）；`0x00220503` 因為要過濾同隊，`rooms.js` 目前只有 `sendAll`／`sendOthers`
     兩個輔助（都不支援依 team 過濾），所以在 handler 裡直接迴圈
     `room.members.values()`，`member.team === 房主自己的 team` 才送。兩者都用
     `getExactMessageBuffer(type, body.length)` + `body.copy(respBody)` 原樣回送，跟已驗證
     的 `0x00220507／0x00220509` 遊戲內聊天回送同一招（`gate.game.dispatch.js` 約
     1090-1110 行，緊接在新 case 後面）。

   新增開關 `ROOM_CHAT_BROADCAST_MODE`（預設 `'enabled'`）——**這點跟
   `docs/backlog.md` 共通規則「新行為預設關閉」字面上不一致，故意這樣做，理由見下面
   「需要高階確認」**。

## `0x00220506`／`0x00220504` ACK 是否還需要保留：判斷依據

`docs/client-dispatch-map.md`（客戶端 dispatcher，只列 server→client）裡完全沒有
`0x00220502`／`0x00220504`／`0x00220506` 這三個 opcode——只有
`0x00220501`／`0x00220503`／`0x00220505`（都標成 `_SN`，跟 `0x00220507／0x00220509`
遊戲聊天一樣是 CQ／SN 共用同一個 opcode 的模式，client 送出用同一個 type，伺服器原樣
送回）。也就是說，這三個 fallback ACK 在客戶端裡沒有任何 handler 認領，一直以來都是被
靜默丟棄。這次改動保留了它們（不在房間時的分支不變），只是把「在房間裡」的情況改成
真正的廣播，回應的 opcode 從 `type+1` 改成 `type` 本身、長度從 6 bytes 變成跟 CQ body
一樣長（實測 258 bytes）。

## 單人回歸樣本變紅：確認範圍

依 `test/README.md`，`login-room-game`／`login-room-shop-buy` 兩個樣本都含 CQ_CREATE
建房後的 `0x00220505` 房間聊天（`login-room-game/recv.jsonl` 第 5 行是建房**前**的
`0x00220501` 大廳聊天，第 7 行是建房**後**的 `0x00220505` 房間聊天——README 原本寫的
「a lobby-chat fallback ack」只點出前者，沒提到後者其實是房間聊天，已在
`test/README.md` 一併訂正，見下方「檔案」）。跑 `node test/replay-golden.js` 只有這兩
個樣本 FAIL，且都只在**同一個 send index（#48）**：

```
[login-room-game] FAIL at send #48: opcode mismatch: expected 0x00220506, got 0x00220505
[login-room-shop-buy] FAIL at send #48: opcode mismatch: expected 0x00220506, got 0x00220505
```

差異只有這一包：從 `0x00220506`／6 bytes 全零 ACK，變成 `0x00220505`／258 bytes 原樣
回送（唯一房間成員是自己，跟建房 CQ 的帳號 1 相同）。`git diff` 確認每個樣本
`expected.jsonl` 只改了那一行，`expected.meta.json` 只有 hash 欄位跟著變。屬於刻意的
行為改變（design §6 step 2 本來就寫明「單人的行為會改變」），已 `--record` 重錄兩個
樣本的基準。`login-dispatch`（不涉及房間）與 `pve-full-match`（單一連線打三場，聊天
只出現在 `login-room-game` 那種登房流程，這個樣本沒有聊天封包）維持不動，全綠。

## 需要高階確認

- **`ROOM_CHAT_BROADCAST_MODE` 預設 `'enabled'`，不是共通規則要求的 `'disabled'`。**
  這是因為任務契約本身（`docs/backlog.md` D1-2 第 3 點）明講「單人行為會改變……這是
  刻意的」並指示直接 `--record` 重錄基準，隱含這一步就是要預設開啟（否則不會變紅、
  不需要重錄）。仍然加了開關（符合共通規則字面上「放在開關後面」的部分），只是預設
  值選了 `'enabled'`，比照同檔案已存在的 `GAME_CHAT_ECHO_MODE`（同樣預設
  `'enabled'`，G7 已實測）。這條預設值本應只有高階能定，這裡先照契約字面指示做，請
  高階確認是否要留著開關本身、或直接拿掉開關寫死。
- **Team 廣播沒有走 `sendOthers`**，因為它要依 `member.team` 過濾而不是依單一
  `exceptAccountId` 排除，`rooms.js` 目前的兩個輔助都覆蓋不到這個情境。是否要在
  `rooms.js` 加第三個 `sendTeam(roomId, team, build)`，還是維持在 handler 裡直接迴圈
  `room.members`（目前做法），留給高階判斷；契約沒有明確要求新增 `sendTeam`，這次沒
  加。
- `0x00220503` Chat_Room_Team 的 CQ 是否真的跟 SN 共用同一個 opcode，
  design §5 表格本身標的是 `⬜ 未知`（只有 `0x00220505` 有 `[LOG]` 實測依據）；這次
  是類推 `0x00220507／0x00220509` 的已驗證模式來實作，還沒有 `0x00220503` 本身的
  `[LOG]` 佐證，需要實機測試多人房才能真正確認。

## PM 審查後修正（PM-F1 fix 1，2026-09-19，中階實作，🟡 待審）

PM 裁決：`ROOM_CHAT_BROADCAST_MODE` 不該同時管 `0x00220505`（有
[LOG] `session-20260918-225741.jsonl` 依據）和 `0x00220503`（沒有
[LOG]／[DLL] 依據客戶端真的送這個 opcode，上面「需要高階確認」第三點
已經點出這個缺口）。新增獨立開關 `ROOM_TEAM_CHAT_MODE`，預設
`'disabled'`；`0x00220503` 改用它判斷是否廣播，關閉時維持 D1-2 之前的
fallback ACK（`type+1`＝`0x00220504`）。`ROOM_CHAT_BROADCAST_MODE` 本身
（管 `0x00220505`）與其預設 `'enabled'` 不變，維持上面已記錄的理由。

`ROOM_TEAM_CHAT_MODE` 宣告改成 `let`（原本跟其他開關一樣是 `const`），
並在 `gate.game.dispatch.js` 尾端 `module.exports` 上掛一個
`_setRoomTeamChatModeForTest(mode)`——只給 `test/room-chat.js` 的隊伍
案例用，測完 `finally` 一定切回 `'disabled'`，不影響其他測試看到的預設
值。`test/room-chat.js` 標頭註解同步更新，說明第 3 個案例會暫時開啟
這個開關。
