## 換算成他說的「銀行」

`D = DeltaTime × CurrentNetSpeed`，下限 `-2D`（語意已由我們自己的組語核對，
`research/2026-09-22-netspeed-budget/high-tier-review.md`）。497 FPS → DeltaTime ≈ 2.01 ms：

| 房主 netspeed | D（bytes/tick） | 下限 `-2D` | 我們實測的投射物遺失 |
|---|---|---|---|
| 10000（原廠） | 20.1 | **40** | 22.5%（16/71） |
| 30000（修補） | 60.4 | **121** | **0.0%（36/36）** |
| 100000（候選 1b） | 201 | 402 | 0.0%（第 2 輪） |

Moon 的條件（100000、1000–1800 FPS）換算下限是 **111–200 bytes**，與他自述的
「110–260 bytes」吻合。

## 🟡 這裡有個對不上的地方，不要忽略

**我們在下限 121 bytes 時是 0% 遺失，他在下限 111–200 bytes 時是 22%。**
他的範圍**涵蓋**我們這個能正常運作的值，所以「銀行大小」單獨**無法**解釋兩邊的差異。

同時，我們自己的兩個點（40 bytes → 22.5%、121 bytes → 0%）**方向上支持**他的機制：
門檻落在 40 與 121 之間。所以比較可能的讀法是

> 🟡 機制方向對，但**閾值不是只由 `-2D` 決定**——他那邊還有別的東西在吃頻寬
> （人數、場景 actor 數、他的量法是加入者端送出 vs 收到），使同樣的下限不夠用。

⬜ 沒查：他的實際條件（幾人房、哪張圖、netspeed 實際值）。要跟他對數字才問得出來。

## 更正（2026-09-22 19:2x，[OBS] 操作者）

**本篇的 497 FPS 不能代表戰鬥中的實際值，據此做的銀行換算全部要重算。**

操作者在人手連按那一輪打完後，於**加入者**視窗開 `stat fps`，實測**約 90**。
本篇量到的 480/497 是**房主端、開著 GAME MENU、沒有移動或開火**的瞬間值
（本篇「量測條件的保留」一節已經標了這三點，但仍低估了差距——是 5 倍，不是小幅）。

重算 `-2D`（`D = DeltaTime × CurrentNetSpeed`）：

| netspeed | @497 FPS（本篇原值） | **@90 FPS（實戰）** | 實測遺失 |
|---|---|---|---|
| 10000 | 40 bytes | **222 bytes** | 22.5% |
| 15000 | 60 bytes | **333 bytes** | 11.1% |
| 30000 | 121 bytes | **667 bytes** | 0%（自動化） |

**本篇「🟡 這裡有個對不上的地方」那一節作廢。** 原文說「Moon 在下限 111–200 bytes
有 22% 遺失，我們在 121 bytes 卻是 0%，所以銀行大小單獨解釋不了差異」——
那是拿錯 FPS 算出來的。用實戰的 90 FPS，我們 30000 時的下限是 **667 bytes**，
遠大於 Moon 的 111–200，**兩邊不再矛盾**，他的機制反而更站得住。

⬜ **仍未量到的**：**房主**戰鬥中的 FPS。決定投射物掉不掉的是房主那一端的銀行，
90 這個數字是加入者的。兩台在同一部機器上跑，房主也在同一場戰鬥，
推測同量級但**沒有量過**。下次開客戶端時補。

教訓：**量 FPS 一定要在「真的在打」的狀態下量**，不是進了戰場就算。
待機畫面與實戰差 5 倍，而這個數字是整條推論鏈的分母。

## 更正的更正（2026-09-22 19:3x，[OBS] 操作者同晚補量）

**上面那段「更正」自己也錯了一半：我拿加入者的 FPS 去算房主的銀行。**

操作者同一晚在兩邊都量了實戰值：

| | 實戰 FPS |
|---|---|
| 加入者 | 約 **83**（小卡頓時掉到 75） |
| **房主** | 約 **300–600** |

**決定投射物掉不掉的是房主那一端的銀行**（`IsNetReady` 走的是房主對加入者那條
connection），所以要用 300–600 算，不是 83。本篇原本量到的 480/497 雖然是
待機畫面量的，**落在房主實戰區間內，方向其實是對的**；上一段「更正」
把它改成 90 並宣告矛盾消失，**那是錯的，作廢**。

重算（房主 300–600 FPS）：

| netspeed | `-2D` |
|---|---|
| 10000 | 33–67 bytes |
| 15000 | 50–100 bytes |
| 30000 | **100–200 bytes** |

Moon 的條件（100000、1000–1800 FPS）是 **111–200 bytes**。
→ **我們 30000 的銀行跟他「會壞」的區間幾乎完全重疊**，而我們自動化量到 0%、
人手量到 5.7%，他量到 22%。**所以本篇最早標的那個「對不上」是成立的，**
差異要從別的地方找（人數、場景 actor 數、量法），不是銀行大小。

## 一個順帶算出來的東西：budget 修補為什麼這麼有效

budget 把下限從 `-2D` 改成 `-(2D + CurrentNetSpeed/4)`。
**`CurrentNetSpeed/4` 不乘 `DeltaTime`**，所以在 30000 下那是固定的 **7500 bytes**——
比 `2D` 的 100–200 bytes 大了一到兩個數量級。

這解釋了為什麼 budget 一加上去就乾淨：它不是把銀行放大一點，是**讓銀行幾乎不再是瓶頸**。
也解釋了為什麼它在高 FPS 的房主上特別有用——`2D` 隨 FPS 升高而縮小，
但 `NetSpeed/4` 完全不受影響。

🟡 這是從修補本身的算式推的，不是量出來的。

## 這一串更正的教訓

同一篇被改了兩次，兩次都是**分母拿錯**：
第一次拿待機值當實戰值，第二次拿加入者的值當房主的值。
**FPS 是整條推論鏈的分母，要標清楚「哪一台、什麼狀態」才能用。**
