## fix round（Sol batch4，2026-09-19）

依 `docs/research/2026-09-19-sol-review/batch4.md`（跨公司審查，Sol）逐點修正，
分成 6 個 commit（每個 fix round 項目一個）+ 1 個測試 commit：

1. **migration 原子性**：`CREATE TABLE IF NOT EXISTS item_equips` 移到
   `beginTransaction()` 之前——MySQL DDL 會隱式 commit，原本包在 transaction 裡
   代表撞到 collision 時的 rollback 撤不回 DDL 造成的隱式 commit，不是真的原子。
2. **拒絕非法 mech_slot**：來源列（`items.mech_type` 對到 `item_equips.mech_slot`）
   若不在 1..8 就整批丟例外＋rollback，逐筆列出違規的 `account_id`／
   `item_id(serial)`／`mech_slot`／`part_slot`；`part_slot` 本來就被 SELECT 的
   `WHERE` 濾掉，這次補一道同樣的檢查當縱深防禦。
3. **重跑安全（主力決定）**：`item_equips` 只要已經有任何列，重跑一律拒絕，除非
   帶 `--force`——因為第 5 點讓 `saveEquippedLoadout` 開啟後完全不再維護
   `items.equipped`／`items.mech_type`，重跑若照舊信任這兩欄會寫進過期資料。
4. **備份提示（主力決定）**：拿掉印出來的 `mysqldump` 指令（`item_equips` 表還
   不存在時第一次執行一定會報錯，不能當可靠備份指令），CLI 改成同時要求
   `ALLOW_REAL_DB_WRITE=1` 與 `E1_BACKUP_CONFIRMED=1`，缺一就印清楚訊息拒絕執行。
5. **`saveEquippedLoadout` 停止碰舊欄位（主力決定）**：`ITEM_EQUIPS_MODE` 開啟時
   完全不再 UPDATE `items.equipped`／`items.mech_type`／`items.part_slot`（不清也
   不設），`item_equips` 是唯一的真相來源；關閉時完全不變。
6. **`buildShopItems()` 也讀 item_equips**：找「這台機目前裝的主武器」（用來推薦
   同系列商店商品）那段改用 `db.getItemsWithEquipViews()`，開啟時不再依賴可能過
   期的 `items.mech_type`／`equipped`；`SHOP_FULL_CATALOG_MODE` 分支跟
   `mechItems`（查 catalog 本身的 `mech_type`，不是帳號擁有狀態）沒動，跟 E1 無關。
   兩個沒有呼叫點的生成器（`sendHangarItemInfo`／`sendHangarAccountData`）各加一行
   註解說明「繞過 E1，接線前要先遷移」，沒有改邏輯（死碼，改了也測不到）。

**測試**：`test/item-equips.js` 的 mock pool 補了真的
`beginTransaction`/`rollback`（存快照、rollback 時還原，不再是空函式），才能真的
驗證「collision 會把同一次 transaction 裡先前已經 insert 的列也撤銷」；新增 4 個
案例（rerun 拒絕、collision 整批 rollback、非法 mech_slot 拒絕、mode-on 時
`items.equipped/mech_type/part_slot` 完全不變），原本的 idempotent 案例補上
`--force`（否則會被第 3 點擋下）。`test/item-equips.js` 共 8 案例全過；
`node test/replay-golden.js` 全綠（`ITEM_EQUIPS_MODE` 預設仍是 `'disabled'`，逐位
元組不變）；其餘 18 個既有 `test/*.js` 全綠。

分支 `flash-wip-e1`，本輪同樣**全程沒有連過真的資料庫**，`tools/
migrate-e1-item-equips.js` 只對著 `test/item-equips.js` 裡的記憶體 mock pool 跑過。
