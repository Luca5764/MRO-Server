## 做了什麼

- 新增 `database/item-share-type.js`：從 Cache.Bin 讀 `GameItemRecord.ShareType`
  （偏移 `+0x4F`，沿用 `room.dispatch.js` 已驗證的 `GAME_ITEM_RECORD_TABLE_START
  =0x2294`／`stride 0x67`／`count 2112` 錨點）與 `UseTime`（偏移 `+0x43`，這不是新
  claim——`room.dispatch.js` 早就在讀同一個偏移當「period」用在
  `SHOP_PERIOD_REPRESENTATIVE_MODE`）。啟動時 lazy load 一次。`node -e` 現場核對
  `32100101`（副武器）→ ShareType=1、`26300101`（主武器）→ ShareType=0，跟設計稿
  §1 的樣本一致。
- `database/db.js` 新增 `item_equips` 讀寫，全部包在 `ITEM_EQUIPS_MODE`（預設
  `'disabled'`）後面：
  - `getItemEquips(accountId)`、`getItemsWithEquipViews(accountId)`——後者是關
    鍵：disabled 時原樣回傳 `getItems()`；enabled 時把 `items` 換成「每筆
    `item_equips` 一個合成列」的陣列（`mech_type`/`part_slot`/`equipped` 蓋掉，
    `id`/`item_id` 不變），讓既有那些用 `item.equipped && item.mech_type===X &&
    item.part_slot===Y` 篩選的讀取路徑**完全不用改篩選邏輯**，只要把
    `db.getItems(...)` 換成 `db.getItemsWithEquipViews(...)` 一行。
  - `saveEquippedLoadout()`：enabled 時不再 `UPDATE items SET mech_type=?`，改寫
    `item_equips`（清掉這台機的舊列 → ShareType==0 的話先刪掉這個 serial 在其他
    機的列 → insert 新列），對應 `ZPage_Hangar.uc:917-924 ItemFree()`。
  - `createAccount()` 的起始裝備同步寫一份 `item_equips`，讓新帳號在兩種模式下
    第一次 WearInfo/Game_User_SN 一樣。
  - `_setItemEquipsModeForTests()` + `ITEM_EQUIPS_MODE` 改成 `let` + 即時 getter
    （`Object.defineProperty`），純測試用逃生口，沒有任何正式路徑呼叫它。
- 讀取端換成 `getItemsWithEquipViews`（disabled 時逐位元組不變，只有這行改）：
  `account.dispatch.js sendAccountData` 的 WearInfo_SN、`gamelogin.dispatch.js`
  自己那份 WearInfo_SN（原本沒被設計稿點名，是我自己 grep 出來的第 4 個生成點）、
  `room.dispatch.js` 的 `sendHangarWearInfo`（WearInfo_SN）與
  `buildSlotChangePayload`（Slot_Change_SA 0x00240108）、
  `room-game-user.sender.js` 的 `equippedBySlot`（Game_User_SN 0x00222112）。
- `room.dispatch.js` 另外兩個 WearInfo/ItemInfo 生成器（`sendHangarItemInfo`、
  `sendHangarAccountData`）是**死碼**（grep 全專案沒有任何呼叫點），沒動；
  `sendHangarAccountData` 裡還有一個跟本任務無關的既有 bug（body-item 迴圈引用
  未宣告的 `slot`），一併記下但沒修（範圍外、且是死碼，改了也測不到）。
- `dispatch/item-info.sender.js` 的 `sendItemInfo()` 改成 `async`：enabled 時
  record+0x08（equipped/IsActive 位元）與+0x16（use type）改成「這個 serial 在
  `item_equips` 有沒有任一列」，不再看 `items.equipped`；+0x10（mech_type）沒動
  ——設計稿 §3 本來就標「⬜ 暫不建議動」。三個呼叫點（`account.dispatch.js`／
  `gamelogin.dispatch.js`／`room.dispatch.js`）都補了 `await`。
- `handleShopPurchase()`（`room.dispatch.js`）：enabled 且該 item_id 是
  ShareType==1、UseTime==0（永久）時，先查帳號是否已擁有同 `item_id`，有的話
  不 INSERT 第二筆 `items`，但照樣扣點、照樣回成功。UseType 欄位偏移全專案沒人
  驗證過，所以租借品（UseTime>0）維持原行為繼續疊，是契約明講的 fallback。
- `tools/migrate-e1-item-equips.js`：冪等、包 transaction、印 before/after 筆數、
  印 `mysqldump` 指令但不執行、UNIQUE 撞到直接丟例外＋rollback。CLI 入口要求
  `ALLOW_REAL_DB_WRITE=1` 才會碰 `db.pool`，本任務全程沒設過這個環境變數，只用
  `runMigration(mockPool)` 對著記憶體假 pool 跑過。
- `test/fixtures/fake-db.js` 補 `item_equips` 相關 mock（`getItemEquips`／
  `getItemsWithEquipViews`／已擁有檢查的 SQL 分支），`ITEM_EQUIPS_MODE` 預設
  `'disabled'`，golden 樣本才不會炸。
- 新增 `test/item-equips.js` 四案例（見下）。

## 怎麼驗證的

- `node --check` 全部改到／新增的檔案，全過。
- `node test/replay-golden.js`：`ALL SAMPLES PASS`（含 `pve-full-match` 8383
  packets），逐位元組跟改動前一致，證明 `ITEM_EQUIPS_MODE='disabled'` 時真的
  什麼都沒變。
- `test/item-equips.js` 四案例，全過：
  1. ShareType=1 副武器（`32100101`）同時掛在 mech1／mech2 的 `item_equips`，
     `sendHangarWearInfo` 送出的 WearInfo_SN 兩台機的 part_slot=2 都讀到同一個
     serial。
  2. ShareType=0 主武器（`26300101`）用真的 `db.saveEquippedLoadout()`（mock
     pool，沒碰 MySQL）從 mech1 換到 mech2：mech1 的 `item_equips` 列消失，
     mech2 多一列，`items` 裡那個 serial 還在（沒被刪）。
  3. `handleShopPurchase` 買一個已擁有的 ShareType=1/永久品：`items` 筆數不變、
     `client.point_` 照樣被扣。
  4. `runMigration()` 對同一個 mock pool 跑兩次：第一次搬 2 筆（跳過
     `equipped=0` 那筆），第二次 `inserted=0`／`skipped=2`，`item_equips` 筆數
     沒變。
- 其餘 `test/*.js`（18 個既有檔）全部 `exit 0`，逐一跑過，沒有 skip。
- 全程只對 fixture／mock pool 寫過資料，沒有 `database/config.json` 指到的真的
  `mro` 資料庫連線、沒跑過 migration 的 CLI 路徑。

## 沒做完或需要主力決定的事

- **`ItemInfo_SN` record+0x10（mech_type）欄位語意仍未知**：契約要我「keep
  today's value or 送第一個 equipped 的 mech_slot，擇一回報」——我選了**維持
  今天的值**（`item.mech_type` 原樣送），因為設計稿 §3 本身就標這欄「暫不建議
  動」，改了會是額外的、沒有組語佐證的假設。如果之後要動這欄，需要獨立一組
  DLL 佐證（設計稿已點名 `0x107095c0` 是該查的位址）。
- **UseType 偏移完全沒人驗證**：買永久共享品不重複的規則我用「ShareType==1 且
  UseTime==0（永久）」判斷，租借品(UseTime>0) 完全沒動，維持原本會疊筆數的行為
  ——這是契約寫明的 fallback，不是我自己選的簡化。如果之後要精確分辨
  UseType（例如租借品到期後的處理），需要新的 DLL/Cache 佐證，這次沒做。
- **`sendHangarItemInfo`／`sendHangarAccountData` 是死碼**：目前全專案沒有任何
  地方呼叫它們（grep 確認），完全沒碰。如果之後有人接上呼叫點，記得
  `sendHangarAccountData` 裡有個跟 E1 無關的既有 bug（引用未宣告的 `slot`
  變數，body-item 迴圈一定會炸），這次沒有修。
- **`buildShopItems`／`sendPackageItems` 等純「擁有清單」用途的讀取路徑刻意沒
  碰**：這些是設計稿本來就沒分析到的路徑，契約也沒點名；`ITEM_EQUIPS_MODE`
  開啟後它們仍然讀 `items.mech_type`（現在語意上等同「最後一次裝備／購買時所在
  的機」），可能會讓商店的「同系列武器」推薦邏輯用到舊資料，但不影響 WearInfo／
  Game_User_SN／Slot_Change_SA／ItemInfo 這幾個目標封包。留給下一輪評估要不要
  處理。
- **開關全程沒打開過（`ITEM_EQUIPS_MODE` 仍是 `'disabled'`）**：本任務完全沒有
  在 `database/db.js` 裡把預設值改掉，`test/item-equips.js` 用
  `_setItemEquipsModeForTests()` 這個測試逃生口在自己的 process 裡暫時打開來測，
  跑完會 reset。**要不要真的把預設值翻成 `'enabled'`、要不要先跑
  `tools/migrate-e1-item-equips.js` 對真的資料庫，都留給高階決定**（契約本身
  也寫明「遷移腳本由高階在 Sol 審過、先備份後才執行」）。
