## 修正 1：`enter-sa.md` 的 `edx`/`esi` 混淆已更正

`docs/research/2026-09-18-d1-room-formats/enter-sa.md` 第 55–61 行原本把 `Enter_SA` 的兩個顯式參數
（`ret 8`）當成同一個指標，結論「`Room_Open`/`Location_Room_Set` 的 index 恆為 0」。本次用
`python3 tools/disasm.py at 0x107e4080 120` 逐條核對（`tools/ghidra/decompile.sh 0x107e4080` 一致），
發現：

- `0x107e40b9 mov edx,[esp+0x54]`（`sub esp,0x4c` 之後、任何 `push` 之前）→ `edx` = 第二個參數，
  之後從未被改寫。`0x107e40bf push esi` 之後 `0x107e40c0 mov esi,[esp+0x54]`（此時 `[esp+0x54]`
  因為 `push` 已經指到別處）→ `esi` = 第一個參數（收到的 `Enter_SA`，`esi+0x10`／`esi+0x12` 是成功
  判斷讀的欄位）。兩者是不同物件。
- `0x107e40fc movzx ebp,[edx+0x10]` 讀的是 `edx`（第二參數）的 body+0，`0x107e4134
  mov edi,[esp+0x64]`（esp 相對位移換算後等於一開始 `mov edx,[esp+0x54]` 讀的同一位址）把 `edx`
  的原始值讀回 `edi`，`add edi,0x12` 取 body+2，用 `0x107e3840` 複製 11 個字元。對照 `notes.md`：
  `Enter_CQ 0x00220231` body 固定 0x1D，+0x00 u16 RoomIndex、+0x02 起 UTF-16 密碼——body+2 正好是
  密碼欄位起點，長度也對得上。**結論：`edx`＝客戶端剛送出的 `Enter_CQ`，`esi`＝伺服器回的
  `Enter_SA`；`Room_Open`/`Location_Room_Set` 的 index 是 `Enter_CQ` 裡的 `RoomIndex`，不是常數 0。**
- `0x107e411f call 0x107086c5`（帶 `edx` 的 body+0 為參數）：`0x107086c5` 是 thunk（`jmp 0x1072c010`），
  `decompile.sh` 解出真正函式名是 `UZNetwork_DJ::RoomList_Name_Get`。`0x1072c010` 逐筆
  `cmp dword[entry],edi`，`entry` 陣列步幅 `0x4c`（76 bytes）；對照
  `~/mro-decrypted/src/ZNetwork/ZNetwork_DJ.uc` 的 `ROOM_SIMPLE_INFO`（欄位順序
  `RoomIndex`／`RoomNumber`／`RoomType`／`RoomName`／...），比對用的是第一個欄位 **`RoomIndex`**，
  不是 `RoomNumber`；命中回傳 `entry+0xc`（第 4 個 4-byte 欄位，正是 `RoomName`）；沒命中回傳指向
  一段全零靜態資料（`0x10814584`）的指標，複製結果是空字串（不是 NULL 判斷觸發，是資料本身全零）。

**對 D1-4 的意義：** 加入房間後 `Room_Open` 顯不顯示得出房名，取決於客戶端本地 `m_LobbyRoomList`
（由 `Room_List_SN 0x00220204` 填）裡有沒有一筆 `RoomIndex` 對得上這次 `Enter_CQ` 送的
`RoomIndex`、`RoomName` 是否已經送對——這正是 `LOBBY_ROOM_LIST_MODE`／`room-list.sender.js` 目前
送的欄位。`RoomNumber`（`UpdateType=1` 才送）／`RoomNameIndex`（bit8）目前只是回填 `RoomIndex`
（`journal/2026-09-19-0330-d1-step4-room-join.md`「不確定／待審處」），這次沒找到任何客戶端讀取
路徑用到它們，**仍是 ⬜**，跟 `RoomList_Name_Get` 用的 `RoomIndex`／`RoomName` 是兩組不同欄位。
不用改實作，`enter-sa.md` 已就地更正（保留原文，標「已更正」），改動位置見該檔第 55 行附近與
「沒有解決」一節。

## 修正 2：`packetlog.js` build 事件補掃 `rooms.js` 的 `let` 開關

原 `SWITCH_RE`（`packetlog.js:322`）只認 `const XXX_MODE = '...'`（大寫底線），只掃 `dispatch/`：
`ROOM_TEAM_CHAT_MODE` 改成 `let`（`dispatch/gate.game.dispatch.js:70`，讓 `test/room-chat.js` 能翻）
後就掃不到；`rooms.js` 的 `roomJoinMode`／`lobbyRoomListMode`（`let`＋camelCase）在檔案範圍外，
兩個問題都存在。改法採 **(a)**：`SWITCH_RE` 改成同時認 `const`/`let`，並認兩種命名
（`[A-Z][A-Z0-9_]*_MODE` 或 `[a-z][a-zA-Z0-9]*Mode`）；`scanSwitches()` 額外把 `rooms.js` 加進掃描
檔案清單（不是把整個掃描根目錄换成上一層，`rooms.js` 刻意放在 `dispatch/` 外的原因跟開關掃描無關，
見該檔檔頭註解）。沒選 (b)：`nonDefault` 的比較基準仍是「跟 `DEFAULT_REF` 同檔同名比較原始碼文字」
（PM 契約要求維持），(b) 要 rooms.js 匯出目前值再讓 `recordBuild` 併入，一樣得對到同一個 diff
機制，複雜度更高但不會多解決什麼問題。

**驗收（`node -e`，未啟動伺服器／未動 9211/30907）：** 把 `rooms.js:83`
`let lobbyRoomListMode = 'disabled'` 與 `dispatch/gate.game.dispatch.js:70`
`let ROOM_TEAM_CHAT_MODE = 'disabled'` 都暫改成 `'enabled'`（原始碼層級，不是呼叫測試用 setter——
`scanSwitches()` 讀的是磁碟上的文字，不是執行期變數，呼叫 `_setXxxForTest()` 不會反映在這裡），
