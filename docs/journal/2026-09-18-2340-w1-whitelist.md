## 改了什麼

工作位置：`~/mro-wt/w1`，分支 `flash-wip-w1`。

1. **`Metal Rage Online Server/config/whitelist.js`（新增）**：讀 `config/allowed-users.json`（`{"users": [...]}`），回傳 `isAllowed(username)`／`status()`。檔案不存在或解析失敗時 `cached = null`（視為關閉），`isAllowed()` 一律回 `true`，行為與 W1 之前完全相同；同時用 `console.warn` 印醒目警告（`!!!!! ... !!!!!`）。比對用小寫：`metalrageserver.sql` 的 `accounts.username` 只寫 `DEFAULT CHARSET=utf8mb4`、沒有明確 `COLLATE`，MySQL 8.0（本機 `mysql --version` 確認是 8.0.46）utf8mb4 的預設 collation 是 `utf8mb4_0900_ai_ci`，是不分大小寫的，所以 `db.getAccountByUsername()` 的 `WHERE username = ?` 本來就不分大小寫比對；白名單如果分大小寫，會出現「設定檔寫 `Lucas`，但登入打 `lucas` 被擋」這種跟 DB 行為不一致的情況。**這條是從 schema 檔＋MySQL 8.0 文件推的，不是對正式 DB 下 `SHOW TABLE STATUS` 查出來的**（這個 worktree 沒有本機 MySQL socket，`mysql -u root` 連不上），如果之後連得到正式 DB，值得補一次直接查證。
2. **`Metal Rage Online Server/config/allowed-users.example.json`（新增，進版控）**：`{"users": ["Lucas"]}`。
3. **`.gitignore`**：加一行忽略 `Metal Rage Online Server/config/allowed-users.json`，跟既有 `database/config.json` 同樣的作法。
4. **`Metal Rage Online Server/dispatch/account.dispatch.js`**：`handleLogin()`（`CQ_LOGIN_WASABII 0x00110151` 觸發）在「一律成功」的 `SA_LOGIN_WASABII` 區塊之前插入白名單檢查。不通過時：
   - `packetlog.connection('whitelist_reject', client.connId_, { username, ip })` 寫一筆事件，console 也印帳號名稱與 `client.socket_.remoteAddress`。
   - 送 `SA_LOGIN_WASABII`，但 body+0x0（uint16）寫 `0x0001`（非零），不是靜默關閉——見下方 DLL 證據。
   - `client.disconnect()`（`socket_.end()`）。
   - `return`，不會呼叫 `db.getAccountByUsername()` 或 `db.createAccount()`，白名單外的使用者不會產生任何 DB 查詢或寫入。
5. **`Metal Rage Online Server/packetlog.js`**：`recordBuild()` 加一個 `whitelist` 欄位（`'off'` 或 `'on(<n> users)'`，來自 `config/whitelist.js` 的 `status()`），console 那行 build log 也印出來。`config/whitelist.js` 不 require 任何 dispatch/packetlog 檔，沒有循環依賴。

## 失敗 SA 的 DLL 依據（不是猜的）

先用 `tools/dispatch-map.py --list` 找到 `ZDispatchAccount::Dispatch @ 0x107039db`，再跑 `tools/dispatch-map.py 0x107039db` 確認 `0x00110152 -> Login_Wasabii_SA`，對上伺服器現有的 `SA_LOGIN_WASABII` 常數。反編譯 `tools/ghidra/decompile.sh 0x10701717`（`ZDispatchAccount::Login_Wasabii_SA`）：

```
if ((*(short *)(param_1 + 0x10) == 0) && (*(int *)(param_1 + 0x12) == 0)) {
    ... UZNetwork_DJ::Location_Gate_Set(...)   // 成功：進 Gate
} else {
    ZNetworkManager::Disconnect(*(ZNetworkManager **)GZNetworkManager_exref, false);
}
```

body 起點對齊 `param_1 + 0x10`（body 只有 6 bytes：`+0x10` 的 short 與 `+0x12` 的 int 剛好是 offset 0 與 2，跟伺服器現有程式碼寫的 `respBody.writeUint16LE(.., 0)` / `writeUint32LE(.., 2)` 完全對得上，不用重新猜排版）。**只要 offset 0 的 uint16 或 offset 2 的 uint32 有一個非零，客戶端自己呼叫 `ZNetworkManager::Disconnect()`**，不會進大廳，也不會顯示任何我們能控制的錯誤訊息（沒看到跳字串的呼叫，這條路徑本身沒有錯誤碼轉訊息的邏輯）。所以送 `code=0x0001` 是有位址證據的失敗格式，不是猜測；`client.disconnect()` 只是伺服器端保險，怕客戶端沒有照預期斷線。
