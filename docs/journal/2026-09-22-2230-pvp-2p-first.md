## 兩件因此確定的事

### 1. `Death_SN` 送給加入者在 PvP 也安全（設計稿 §5 的處置成立）

premises P5 說安全、Moon B11 說不要送。設計稿依 M2 的 945 次 PvE 紀錄採 P5，
但標了「PvP 2 人實跑時第一件要看的就是加入者有沒有崩潰」。
**現在看了：`Death_SN` 送進 2 人房、加入者收到後存活、個人分數正確更新。**
→ P5 在 PvP 也成立，Moon 的 B11 對 `Death_SN` 確實過度保守。

### 2. 設計稿 U3 有答案了：個人分數會跟著 `Death_SN` 更新，隊伍總分不會

- **個人**：`P 0010` 跳了 → `Death_SN` 本身足以更新個人分數。
- **隊伍**：計分板 `000` 不動 → **隊伍總分要靠伺服器另外記、另外同步**。
  這正是 T2（`PVP_KILL_TRACKING_MODE`）要做的，同步方式候選是 `Timeout_SN`
  （Moon 說對加入者安全，🟡）。**T2 是必要的，不是可有可無。**

## 同一輪踩到的兩件事

1. **重開機後 MySQL 不會自己起來**，而伺服器連不到資料庫時**不會停下來**，
   而是默默用預設空帳號頂上——第一次跑時房主變成「Player／訓練兵」並跳出新手任務彈窗，
   登入步驟因此失敗。表面上「能登入」，其實整個環境是假的。
   另外 `service mysql status` 會**誤報「停著」**（它找的 pid 檔名不對，實際是 `Lucas.pid`），
   要用 `pgrep mysqld` 或測 3306 連接埠才準。
2. **PvP 房的設定欄幾乎全空**（遊戲類型、人數、目標分數、遊戲時間、目標回合）——
   操作者發現並指出要先處理。「目標分數」與「遊戲時間」正是 T3／T4 判勝負用的值。
   已派唯讀調查（`research/2026-09-22-d2-tdm/room-settings-blank.md`）。

## 補：PvP 房設定欄全空與「地圖選不了」的根因（2026-09-22 22:4x）

唯讀調查 `research/2026-09-22-d2-tdm/room-settings-blank.md`（196 行，explorer）。

### 設定欄全空

**`dispatch/room/room-map.sender.js:139-141`**（高階已核對）：

```js
if (!ctx.isTrueCampaign) {
    return;
}
```

`sendRoomMapPackets()` 對**所有 PvP 房完全不送** `Map_Change_All_SN 0x00220226`＋`Map_Change_One_SN 0x00220223`。
而 `Map_Change_One_SN` 是**唯一**把真實 Time／Round／Kill／Goal 寫進客戶端 `RoomInfo.MapInfo[]` 的封包
（[DLL] `0x107eb771-0x107eb7a0`：body `+0x03` MapTime、`+0x05` MapRound、`+0x06` MapKill、`+0x08` Goal）。
客戶端 `ZPanel_RoomInfo.uc:361-438` `SetRoomInfo()` 查不到就**五格一起放棄**、提早 return；
「隊伍平衡」直接讀 `RoomInfo.IsBalance`、不經這條路 → **只有它有值**。完全吻合截圖。

`isTrueCampaign` 的公式 `(roomType===1) || (gameMode===4||5)` 中，`gameMode` 讀的是 PlayGoal 欄位
（`pvp-start-gap.md` Q4），真實封包恆為 0 → **這個布林實際上等同 `roomType===1`**，PvP 恆為 false。

**伺服器其實有存對的值**：`createPlayTime_` 已存、也已用在戰場 `Game_Info_SN +0x13`（所以戰場 08:00 正確），
只是房間畫面要的那包被擋住。→「戰場對、房間畫面空」。

### 「地圖選不了」

操作者選地圖時：

```
Map_Change_One_CQ recv  00 0704 1400 01 9600 0000
Map_Change_One_SN send  00 0704 1400 02 9600 0000
```

對照上面的欄位：地圖 **1031**、MapTime **20**、**MapRound 客戶端送 1 → 伺服器改成 2**、MapKill **150**。
客戶端自己帶了 **20 分鐘／150 殺**——正是韓版原廠 TDM 預設。
伺服器把回合數從 1 改成 2（`gate.game.dispatch.js:267-280` 的 `MAP_CHANGE_ONE_SA_EXPERIMENT` 固定欄位邏輯）。
🟡 高度懷疑這是「選不了」的原因（客戶端收到與自己送出不同的值），**未實測**。

順帶：**TDM 的擊殺目標在 `MapKill`（`+0x06`），不是 `Goal`（`+0x08`）**——這對 T4 很重要。

### explorer 標的三個不確定（明天處理前要看）

1. 「選擇地圖」那格有值，判斷是 UI 殘留建房時的選擇，**不是伺服器送對**。
2. `gate.game.dispatch.js:1241` 把 Create_CQ `body[6]` 當地圖讀，但 ✅ 欄位表說那是 PlayRound。
3. R4（`journal/2026-09-18-11`）的 ❌ 測的是設定變更彈窗 `ZPopup_RoomSet`，本題是房間主畫面 `ZPanel_RoomInfo`，
   **不要假設 R4 的結論適用**。

### 修法方向（明天；PM 已說明同類問題要另開旗標，不要改 `isTrueCampaign` 的語意）

另開旗標讓 PvP 房也送 `sendRoomMapPackets()`，初始值用已存的 `createPlayTime_` 等；
並讓 `Map_Change_One_SN` 照實回傳客戶端送來的 MapRound，不要改成 2。

### 這改寫了上面的判讀

1. **客戶端畫得出這些值，UI 沒問題**——問題只在「建房當下沒送到」。回房時**某個封包**把 `RoomInfo.MapInfo[]` 補齊了。
   → 修法可能比「另開旗標送 `sendRoomMapPackets()`」更單純：找出回房時送的是哪一包，**建房時也送一次**。
   ⬜ **是哪一包還沒查**（候選：操作者在房裡改地圖觸發的 `Map_Change_One_SN`，或回房流程的某個 bootstrap）。
2. 「目標回合 **1回合**」——伺服器先前回傳的 MapRound 是 2，這裡卻顯示 1。
   → 上面「地圖選不了是因為 MapRound 被改成 2」的 🟡 推論**要打折扣**：顯示值不是從那包來的，或客戶端另有來源。
