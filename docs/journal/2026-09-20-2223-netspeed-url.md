# NETSPEED 塞進伺服器送出的連線 URL？（中階，2026-09-20 22:23）

任務契約見上一手的交付訊息。承 `2026-09-20-2030-same-machine-and-netspeed.md` 第 8 節：那篇已確認客戶端讀的是自己那條連線的 `CurrentNetSpeed`（Engine.dll `0x1047f9a4`）握手送出去，而握手送的值（10000）跟我們送給客戶端的任何欄位無關——這篇要核對的是「反過來」：我們能不能透過 `Ready_Host_SN` 這個 S→C 封包的欄位，讓客戶端組出的連線 URL 帶 `?NETSPEED=`。

## 1. 找到真正的處理函式（不是原始 func dump 那個表）

`0x00420115 Ready_Host_SN` 的匯出位址 `0x1070a254` 只是一個 thunk（`jmp 0x107d5700`）。`tools/disasm.py func` 從匯出位址往下印 200 行时，印出的其實是**一整排相鄰、互不相干的匯出 thunk**（每 5 byte 一個 `jmp`），只有第一條 `jmp` 屬於 `Ready_Host_SN`。真正的函式本體在 `0x107d5700`，核對方式：讀該位址附近的字串常數，確認是 `"ZDispatchGame::Ready_Host_SN"`、`"Failed - Active"`、`"IP : %s, PORT : %d"`（file offset 對照 VA，見 `docs/research/2026-09-20-netspeed-url/ready_host_sn_disasm.txt`）。

## 2. 欄位與長度：確認組語，但數字跟舊註解不同

`gate.game.dispatch.js:405-414` 的註解說「只取前 15 個字元」。反組譯 `0x107d5700` 本體：

- `port`：讀自 frame 絕對偏移 `0x10`（`movzx esi, word ptr [ebp+0x10]`，`0x107d57b8`）。
- IP/host 字串：讀自 frame 絕對偏移 `0x13`（`lea edi,[ebp+0x13]`，`0x107d575d`）——這跟 `buildReadyHostSnMsg` 的 `respBody.write(..., 0x03, ...)` 對得上（`0x13 - 0x03 = 0x10`，16-byte 封包頭）。
- 長度夾值：先呼叫 Core.dll `winGetSizeUNICODE`（import `0x1091b834`）量出字串字元數，`cmp eax,0x10; jge` 把它**夾在 16（0x10），不是 15**（`0x107d5778/0x107d577b`）。夾完呼叫 `winToUNICODE`（import `0x1091b830`）轉寬字元，terminator 寫在 `dest[esi]`。

→ **更正舊註解：實際上限是 16 個寬字元，不是 15。** 但這個差一個字元對結論沒有影響（見下）。

## 3. 有沒有第二個欄位可以塞 `?NETSPEED=`：沒有

`0x107d5700` 本體只讀這兩個欄位（port、16-char 字串），沒有第三個欄位。字串轉完之後，程式碼把它跟 port 一起丟進 `UClass::GetDefaultObject`（Core.dll import `0x1091b990`）拿到的某個 UObject default instance，經 thunk `0x10709f4d -> 0x1071a570` 把兩個值**存進 UObject 的成員欄位**（字串存 `[this+0xfb0]`，port 存 `[this+0xfbc]`）就返回了。**`ZNetwork.dll` 裡完全沒有 `"%s:%d/%s"` 這種格式化字串、也沒有字串串接**——真正組 URL（含附加 `?team=0`）的邏輯不在這支 DLL 裡，很可能是 UnrealScript bytecode 或更底層的 `Engine.dll` 呼叫鏈，超出這次的時間範圍與工具（disasm.py 只吃 DLL）。

**尚未核對**（超出範圍，留給下一手）：`?team=0` 究竟是誰接上去的、有沒有辦法從別的封包塞第二個 `?option`。目前只能確認「不是這支封包的欄位塞的」。

## 4. 就算多 1 個字元也塞不下

即使把上限當 16（比舊註解多 1），這 16 個字元幾乎全被 IP 位址本身吃光：任何真實的 LAN／VPN IPv4（例如 `192.168.0.10` 13 字元、`10.8.0.5` 8 字元）扣掉之後剩不到 10 個字元，塞不進 `?NETSPEED=100000`（17 字元）或任何有意義的選項。**這條路被欄位長度本身擋死，不是靠精確到 15 還是 16 才能判斷。**

## 5. 查過的另一個候選封包：`HostChange_SN`（0x00420121），沒有欄位

`docs/client-dispatch-map.md` 裡跟連線/位址相關的 S→C opcode 只有 `Ready_Host_SN` 一個帶欄位。順手核對了同一組（`ZDispatchGame`）唯一另一個聽起來相關的 `HostChange_SN`（thunk `0x10702cf2 -> 0x107d5a00`）：反組譯後**完全不讀封包 body**，只讀自己物件的 flag byte，是純通知型（見 research 檔末段）。不是額外的資料來源。

## 結論（🟡 待審，中階不標 ✅）

**伺服器端無路可走。** 擋死的是 `ZNetwork.dll` `0x107d5700`（`Ready_Host_SN` 本體）對 IP/host 字串欄位的 16 寬字元硬上限（`0x107d5778` `cmp eax,0x10`），這個欄位已經被 IP 位址本身佔滿，塞不進任何 `?option`；而真正組出最終 URL（含 `?team=0`）的程式碼不在 `ZNetwork.dll` 裡，這支 DLL 在存完 IP/port 到 UObject 欄位後就結束了。
