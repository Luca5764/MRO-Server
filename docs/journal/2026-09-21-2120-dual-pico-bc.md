### ✅ 實測：戰鬥中的 CN **全部走房主的連線**

同一輪的伺服器 session log：

```
51081345 send 0x00222104 conn=28(host)   51081345 send 0x00222104 conn=30(joiner)
51084121 recv 0x00230151 conn=28         ← BeginRound_CN 只在房主
51092846 recv 0x00230101 conn=28         ← ChangeSlot_CN
51092848 recv 0x00230103 conn=28         ← Respawn_CN
51099722 recv 0x00230101 conn=28         ← 第二次（另一個玩家）
51099724 recv 0x00230103 conn=28
```

**加入者的 conn=30 只收到廣播的 SN，一個 CN 都沒有。**

這正是 Moon 的 `protocol_objective.en.md` §1 所說的「Every in-game CN arrives on the HOST's
socket；joiner 的連線在對戰中只有 keep-alive」——**現在有我們自己的實測資料。**

**後果**：所有「在加入者連線上等戰鬥 CN」的完成條件都永遠等不到。
`enter_battle` 要改成在**房主的 game conn** 上過濾，並用 body 裡的 UserIndex 分辨是誰
（`ChangeSlot_CN` body len=3：user u16 ＋ slot u8）。

## netspeed 手測：**結論撤回，資料不足**

C 段停在 `enter_battle` 時兩個客戶端還在戰鬥中，我手動送了主控台指令想直接取得讀數。

房主 log（檔案本身，非 logwatch）只有**兩行** `Client netspeed is 10000`，
都在加入的那一刻（第 166、169 行，夾著 `Login Info InName=mrotest` 與 `START MATCH`），
**第 170 行開始就是客戶端關閉的拆除訊息，中間沒有第三行**。

我原本據此推論「NETSPEED 只在加入時協商一次」。**但操作者在旁觀看，回報「兩個客戶端進遊戲後
什麼都沒發生、沒有任何主控台輸入的動作」**——也就是說指令**很可能根本沒進到遊戲裡**。

**所以「沒有第三行」不能歸因於「不會重新協商」，只能歸因於「指令沒送到」。結論撤回。**

🟡 可能的原因：**F24 是 toggle**。送 F24 後截圖確認主控台是開著的（`(>` 在畫面上），
但那之後**隔了 34 秒**才打字（中間做了截圖與畫面判定）。若主控台在那段期間關掉，
打的字就進了遊戲而不是主控台。

**下一輪要補的三件事**（都很便宜）：
1. **打字後立刻再截一張**，確認文字真的在主控台裡；
2. **F24 到打字之間不要插任何動作**，一氣呵成；
3. 跟著跑一次 `stat net` 看 `Speed` 欄，作為加入者端的獨立驗證。

**仍然成立的部分**：房主在加入者進場時記錄了兩行 `Client netspeed is 10000`。
這與 2026-09-20 的 [TEST]（兩份 `IpDrv.dll` 都改 100000 後，加入者 `stat net` 顯示 100000、
房主仍記錄 10000）方向一致，但**單憑今天的資料不足以下結論**。
