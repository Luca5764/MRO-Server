# T1: Game_Info_SN TimeLimit follows room PlayTime (中階實作，🟡 待審)

## 任務

`docs/backlog.md` T1。目標：`Game_Info_SN 0x00222111` 的 TimeLimit 欄位改用房間的
PlayTime，不再寫死 10 分鐘。前置分析由高階審過，本篇只做實作與回歸驗證，不做
新的組語調查。

## 依據（照搬自契約，附完整位址覆核）

- [DLL] `0x107d4fa7 movzx ebp, word ptr [eax+0x23]`，handler 本體
  `0x107d4f50`（`ZDispatchGame::Game_Info_SN`，thunk `0x107079af`）：body+0x13
  的 u16 被讀出後放進 `Game_Info_Set` 的第 7 個參數，寫入 `[this+0xfd4]`。
  `dispatch/gate.game.dispatch.js` 現有的欄位表（`sendGameInfoSn` 函式頂端註解，
  約行 264-282）已經記著這張對照，本次沒有再重新反組譯，只核對行號與 offset
  對得上：`body.writeUInt16LE(timeLimitMinutes, 0x13)` 確實對應 p7/`[0xfd4]`。
- [SRC] `~/mro-decrypted/src/ZBase/DefaultGameInfo.uc:361,369,182`：
  `TimeLimit` 乘以 60 之後才拿去跟遊戲內剩餘秒數比較，單位是分鐘，跟 DLL 端
  `[0xfd4]` 的解讀一致。
- [CODE] `dispatch/gate.game.dispatch.js` 原本 `const timeLimitMinutes = 10;`
  是寫死的（grep `timeLimitMinutes` 命中該行）。
- [CODE] 房間 PlayTime 的來源：`Map_Change_One_CQ 0x00220221` 的 w2 欄位，
  `dispatch/gate.game.dispatch.js` 的 `case 0x00220221` 內
  `client.mapChangeOneTime_ = incomingFields.w2;`（[DLL] `0x107eb78b`
  `ZDispatchRoom::Map_Change_One_CQ`）。實測 log 中曾出現 60（分鐘），比對
  `test/golden/pve-full-match/recv.jsonl` 第 17 行 `0032233c000500000000`：
  `w1=9010`(map)、`w2=0x003c=60`、`b5=5`(round)，跟已知 log 實例一致。

## 改動

- 新增開關 `GAME_INFO_TIME_LIMIT_MODE = 'disabled'; // 'disabled' | 'room'`
  （`dispatch/gate.game.dispatch.js` 約行 32-37，緊接在既有 `_MODE` 常數群組
  後面）。
- `sendGameInfoSn` 內 `timeLimitMinutes` 由 `const` 改 `let`：`'room'` 且
  `client.mapChangeOneTime_` 有值時採用它，否則維持 10（約行 293-304）。
  console log 加上 `(${timeLimitSource})` 標示這次送出採用的是 `hardcoded`
  還是 `room`（約行 311）。
  註解寫明觸發點：由客戶端按 F5 開戰觸發（`sendGameInfoSn` 在 game-start
  handshake 與 scene-6 地圖 resend 兩處被呼叫，見同函式上方既有註解）。
- `session.js` 的 `CARRIED` 清單加入 `'mapChangeOneTime_'`（原本 32-39 行，只
  加這一個欄位）。理由：客戶端開戰換地圖會斷線重連，`mapChangeOneTime_`
  只在 Map_Change_One_CQ 那條連線上设定，若不延續，`'room'` 開關在重連後的
  `sendGameInfoSn`（例如 scene-6 resend）就會讀不到值、退回 10，開關形同虛設。
  這不算「同時改兩個變數」：`disabled` 時這個欄位唯一的讀取點是
  `room-map.sender.js:52` 的 `Map_Change_One_SN`，而那條路徑跟寫入點在同一條
  連線上完成（同一次 CQ→SN 往返），延續它不改變 disabled 時的任何輸出——下面
  的回歸測試（開關關閉，4 個樣本全綠）就是這個論證的證據。

## 回歸驗證

開關維持 `disabled`（commit 前狀態）：

```
[login-dispatch] PASS (14 packets)
[login-room-game] PASS (50 packets)
[login-room-shop-buy] PASS (363 packets)
[pve-full-match] PASS (8383 packets)
ALL SAMPLES PASS
```

暫時改成 `'room'`（只在本機跑，跑完已還原成 `disabled`，未 commit 這個狀態）：

```
[ZGateGameDispatch] >> Sent Game_Info_SN ... [room state [delayed]] ... timeLimit=10 (hardcoded) ...
[ZGateGameDispatch] >> Sent Game_Info_SN ... [server-driven: scene-6 map] ... timeLimit=60 (room) ...
[pve-full-match] FAIL at send #1206: body mismatch on op=0x00222111 at byte offset 0x13:
  expected .. 00000000020032230a000500000000 .., got .. 00000000020032233c000500000000 ..
SOME SAMPLES FAILED
```

`0x0a`(10) 變成 `0x3c`(60) 剛好對上 body+0x13。前兩次 `Game_Info_SN`（`room
state [delayed]`／`room state [retry after scene change]`）在樣本裡發生在
`Map_Change_One_CQ`(recv #17) 之前，`mapChangeOneTime_` 還沒設定，所以仍是
10——這符合預期，不是 bug。改回 `disabled` 後 4 個樣本重跑全綠（同上），確認
沒有殘留改動。

## 關於 P3（547 秒停住）

`docs/journal/2026-09-18-18-pve-hard-flow.md` 記錄困難房（9012／Round 10）在
547 秒左右停住、沒有 Campaign／EndGame。**TimeLimit 不是這次停住的原因**：
寫死的 10 分鐘 = 600 秒，547 < 600，客戶端端的計時器根本還沒到期。停住的真正
原因仍待 P3 後續調查（round manager／Campaign 觸發），本任務不擴大範圍。
